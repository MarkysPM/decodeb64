Base64 vs Base64URL : quelle différence ?

Novembre 2026 · 6 min de lecture

Si vous avez déjà collé une chaîne dans un décodeur Base64 et obtenu une erreur alors qu'elle « ressemblait » à du Base64, il s'agissait très probablement de Base64URL. Les deux encodages appartiennent à la même famille et ne diffèrent que par quelques caractères, mais ces quelques caractères décident si une chaîne survit dans une URL, un cookie, un nom de fichier ou un JWT.

Le Base64 standard en une minute

Le Base64 standard, défini dans la RFC 4648, transforme des octets quelconques en texte à l'aide de 64 caractères imprimables : A–Z, a–z, 0–9, plus + et /. Chaque groupe de trois octets devient quatre caractères. Quand la longueur de l'entrée n'est pas un multiple de trois, la sortie est complétée par un ou deux signes = pour que la longueur finale soit toujours un multiple de quatre.

Par exemple, les trois octets du texte Man donnent TWFu, les deux octets de Ma donnent TWE= et l'octet unique M donne TQ==.

Ce que change le Base64URL

La même RFC définit un second alphabet, dit « sûr pour les URL et les noms de fichier ». Il fait exactement deux substitutions et traite le bourrage différemment :

  • + devient - (le plus devient un tiret)
  • / devient _ (la barre oblique devient un tiret bas)
  • le bourrage = est en général supprimé : la norme permet de l'omettre et la plupart des générateurs Base64URL le font

Tout le reste est identique : le même regroupement de 6 bits, la même surcharge de 33 % et le même algorithme de décodage. Seul l'alphabet change.

Pourquoi cette différence existe

Les caractères +, / et = ont tous un sens particulier quelque part dans l'infrastructure web :

  • / sépare les segments de chemin dans les URL et les systèmes de fichiers ; une chaîne Base64 qui en contient peut casser une route ou un nom de fichier.
  • + est interprété comme une espace dans les données application/x-www-form-urlencoded, si bien qu'un analyseur de query string peut le corrompre sans prévenir.
  • = sépare les clés des valeurs dans les query strings et les cookies.

Vous pouvez les encoder en pourcentage (%2B, %2F, %3D), mais la valeur s'allonge et il est facile de la double-encoder par erreur. Le Base64URL évite tout le problème en n'utilisant que des caractères sûrs partout : lettres, chiffres, tiret et tiret bas.

Un exemple concret

Prenons les deux octets 0xFB 0xFF. En binaire : 11111011 11111111, qui se regroupent en valeurs de 6 bits : 62, 63 et 60. Elles correspondent à +, / et 8 :

Standard Base64 : +/8=
Base64URL       : -_8

Les données sont les mêmes ; seule leur écriture change. Remarquez l'absence de = à la seconde ligne, convention habituelle du Base64URL.

Où vous rencontrerez du Base64URL

  • JWT (JSON Web Tokens). L'en-tête, la charge utile et la signature sont en Base64URL sans bourrage. Voir notre guide sur le décodage des jetons JWT.
  • OAuth 2.0 et PKCE. Le code challenge PKCE est un hachage SHA-256 encodé en Base64URL.
  • Web Push et WebAuthn. Clés, défis et identifiants de credentials sont échangés en Base64URL.
  • URL signées, identifiants de session et ID courts générés par de nombreux frameworks.

Le Base64 standard reste le choix par défaut pour les pièces jointes d'e-mail (MIME), les certificats PEM, les data URI et la plupart des cas de « stocker un blob binaire dans un champ texte ».

Convertir de l'un à l'autre

Les algorithmes étant identiques, la conversion se réduit à remplacer des caractères et à ajouter le bourrage.

Base64URL vers Base64 : remettez les caractères d'origine et rétablissez le bourrage pour que la longueur soit un multiple de quatre :

// JavaScript
function base64urlToBase64(s) {
  let b64 = s.replace(/-/g, '+').replace(/_/g, '/');
  while (b64.length % 4) b64 += '=';
  return b64;
}

Base64 vers Base64URL : l'inverse, en supprimant le bourrage :

function base64ToBase64url(s) {
  return s.replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

En Python, la bibliothèque standard fournit déjà des aides : base64.urlsafe_b64encode() et base64.urlsafe_b64decode(). Elles conservent le bourrage = ; supprimez-le vous-même si le système récepteur attend la forme sans bourrage. En Node.js, vous pouvez passer 'base64url' comme encodage à Buffer.toString() et Buffer.from().

Erreurs courantes

Décoder du Base64URL avec un décodeur Base64 strict. Un décodeur strict rejette - et _ et se plaint du bourrage manquant. C'est la cause la plus fréquente des erreurs « invalid character » et « incorrect padding » lors de l'inspection de jetons.

Mettre du Base64 standard dans une URL sans l'encoder. Le + devient une espace côté serveur et les octets décodés sont corrompus, souvent sans aucune erreur.

Supposer que le bourrage est toujours présent. De nombreuses bibliothèques produisent une sortie sans bourrage ; écrivez des décodeurs qui acceptent les deux formes.

Mélanger les alphabets. Une chaîne qui contient à la fois + et -, ou / et _, n'est valide dans aucun des deux. Cela signifie généralement que deux systèmes l'ont concaténée ou modifiée.

Lequel utiliser ?

Utilisez le Base64URL quand la valeur circule dans une URL, une query string, un cookie, un nom de fichier ou un en-tête HTTP, et chaque fois qu'une spécification (JWT, PKCE, WebAuthn) l'exige. Utilisez le Base64 standard pour MIME, PEM, les data URI et les champs de stockage où + et / ne posent pas de problème.
