Comment décoder des tokens JWT et inspecter leurs claims

Août 2026 · 6 min de lecture

Les tokens JWT constituent l'épine dorsale des systèmes d'authentification modernes. Que vous déboguiez un problème de connexion, inspectiez les claims renvoyés par une API, ou appreniez le fonctionnement interne d'OAuth 2.0, savoir décoder un JWT est une compétence essentielle pour tout développeur. Ce guide vous accompagne étape par étape dans ce processus.

La structure d'un JWT

Un JWT (JSON Web Token) se compose de trois parties séparées par des points :

[header].[payload].[signature]

Un vrai JWT ressemble à ceci :

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Chaque partie utilise l'encodage Base64URL — et non le Base64 standard. Base64URL remplace + par -, / par _, et supprime le remplissage =, ce qui rend le token sûr à utiliser dans les en-têtes HTTP et les URL.

Partie 1 — Le Header

La première partie encode un objet JSON décrivant le token :

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9

Décodé :

{"alg":"HS256","typ":"JWT"}

Le champ « alg » indique au serveur quel algorithme cryptographique a été utilisé pour signer le token. Les valeurs courantes incluent HS256 (HMAC avec SHA-256), RS256 (RSA avec SHA-256) et ES256 (ECDSA avec SHA-256).

Partie 2 — Le Payload (Claims)

La deuxième partie encode les claims — les données transportées par le token :

eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ

Décodé :

{"sub":"1234567890","name":"John Doe","iat":1516239022}

Noms de claims standard :

  • sub (subject) — généralement l'ID de l'utilisateur
  • iat (issued at) — timestamp Unix de la création du token
  • exp (expiration) — timestamp Unix d'expiration du token — vérifiez ce champ lors du débogage des erreurs « token expiré »
  • iss (issuer) — le serveur ou service ayant créé le token
  • aud (audience) — le destinataire prévu du token
  • jti (JWT ID) — un identifiant unique du token, utilisé pour empêcher les attaques par rejeu

Les claims personnalisés peuvent contenir n'importe quelle donnée : rôles utilisateur, permissions, adresses e-mail, niveaux d'abonnement — tout ce dont l'application a besoin.

Partie 3 — La Signature

La troisième partie est une signature cryptographique, et non un objet JSON encodé en Base64URL. Elle est créée en hachant le header et le payload avec une clé secrète. Vous ne pouvez pas la décoder en texte lisible. Seul le serveur détenant la clé secrète peut la vérifier.

Comment décoder un JWT étape par étape

Étape 1 : Copiez la chaîne du JWT depuis votre application, les outils de développement du navigateur, ou une réponse d'API.

Étape 2 : Divisez-la selon les points. Vous obtiendrez trois parties. La troisième partie (signature) ne peut pas être décodée en texte lisible.

Étape 3 : Prenez la première ou la deuxième partie (header ou payload) et collez-la dans decodeb64.com. Le décodeur gère automatiquement le Base64URL — inutile de remplacer manuellement - par + ou _ par /.

Étape 4 : Le JSON décodé vous montre les claims. Si vous déboguez un problème d'authentification, vérifiez d'abord le champ exp — convertissez le timestamp Unix en date lisible pour voir si le token a expiré.

Décoder vs vérifier

Une distinction essentielle : décoder un JWT n'équivaut pas à le vérifier. N'importe qui peut décoder le payload d'un JWT et lire les claims. Ce qui rend les JWT sécurisés, c'est la signature — seul le serveur possédant la bonne clé secrète peut vérifier que le token est authentique et n'a pas été altéré.

Ne faites jamais confiance aux claims d'un JWT dans votre application sans vérifier la signature côté serveur à l'aide d'une bibliothèque JWT appropriée. Le décodage ne sert qu'à l'inspection et au débogage.

Scénarios courants de débogage JWT

« Le token est invalide » — Le token peut être mal formé ou corrompu. Collez-le dans un décodeur pour vérifier sa structure.

« Le token a expiré » — Décodez le payload et vérifiez le claim exp. Convertissez le timestamp Unix pour confirmer quand le token a expiré.

« Les claims sont incorrects » — Décodez le payload pour voir exactement quels claims contient le token. Le problème vient souvent du fait que le token a été émis avant un changement de permissions.

« Échec de la vérification de la signature » — Cela ne peut pas être débogué par décodage. Vérifiez que le serveur utilise la bonne clé secrète ou publique pour l'algorithme indiqué dans le header.

Essayez maintenant

Collez votre JWT dans decodeb64.com. L'outil détecte automatiquement l'encodage Base64URL et décode le header et le payload. Vous pouvez aussi utiliser le mode « Décoder chaque ligne séparément » si vous avez plusieurs tokens à inspecter à la fois.

Décoder des tokens JWT est une tâche quotidienne pour les développeurs back-end et front-end travaillant avec des systèmes d'authentification. Comprendre la structure en trois parties et la différence entre décodage et vérification vous donne le contrôle lorsque des problèmes d'authentification surviennent.
