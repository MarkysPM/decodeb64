Décoder du Base64 en ligne de commande : Linux, macOS et Windows

Novembre 2026 · 6 min de lecture

Pas besoin de navigateur ni de script pour décoder du Base64. Tous les grands systèmes d'exploitation fournissent un outil qui le fait en une ligne, pratique quand vous lisez des journaux en SSH, inspectez un jeton dans un pipeline ou restaurez un fichier depuis une variable de CI. Ce guide présente les commandes pour Linux, macOS et Windows, ainsi que les petites différences qui les font échouer.

Linux : la commande base64

GNU coreutils inclut base64 sur pratiquement toutes les distributions. Ajoutez -d (ou --decode) pour décoder :

echo 'SGVsbG8sIFdvcmxkIQ==' | base64 -d
# Hello, World!

Utilisez printf '%s' ou echo -n quand la valeur vient d'une variable, afin qu'un retour à la ligne final ne fasse pas partie de l'entrée :

printf '%s' "$TOKEN" | base64 -d

Pour décoder un fichier vers un autre fichier, redirigez la sortie. Envoyez toujours les résultats binaires dans un fichier et non dans le terminal :

base64 -d encoded.txt > photo.png
file photo.png
# photo.png: PNG image data, 800 x 600, 8-bit/color RGBA

Le base64 de GNU tolère les retours à la ligne dans l'entrée mais rejette les autres parasites avec base64: invalid input. L'option -i (--ignore-garbage) lui fait ignorer les caractères hors alphabet, ce qui est utile mais peut masquer des données corrompues ; utilisez-la à bon escient.

macOS : le même outil, avec des options légèrement différentes

macOS fournit la version BSD. Les anciennes versions utilisent un -D majuscule pour décoder, et les récentes acceptent aussi -d. Si une option provoque une erreur, essayez l'autre :

echo 'SGVsbG8sIFdvcmxkIQ==' | base64 -D
echo 'SGVsbG8sIFdvcmxkIQ==' | base64 -d     # newer macOS versions

L'outil BSD lit et écrit des fichiers avec -i et -o :

base64 -D -i encoded.txt -o photo.png

Sous macOS, vous pouvez aussi décoder directement depuis le presse-papiers, le moyen le plus rapide d'inspecter ce que vous venez de copier :

pbpaste | base64 -D

Sous Linux, l'équivalent utilise xclip -o ou wl-paste.

Windows : PowerShell

PowerShell peut appeler .NET directement. FromBase64String renvoie des octets ; convertissez-les en texte quand le contenu est du texte :

$bytes = [Convert]::FromBase64String('SGVsbG8sIFdvcmxkIQ==')
[Text.Encoding]::UTF8.GetString($bytes)
# Hello, World!

Pour restaurer un fichier à partir de Base64 :

$b64 = Get-Content .\encoded.txt -Raw
[IO.File]::WriteAllBytes("$PWD\photo.png", [Convert]::FromBase64String($b64))

.NET ignore les espaces blancs et les retours à la ligne dans l'entrée, donc un fichier découpé en lignes ou le retour final de Get-Content -Raw ne posent pas de problème. En revanche, il lève une erreur sur les caractères invalides et sur une longueur incorrecte. Utilisez [IO.File]::WriteAllBytes avec un chemin complet, car .NET résout les chemins relatifs par rapport au répertoire du processus et non à votre emplacement actuel dans PowerShell.

Windows : certutil

Le certutil intégré fonctionne depuis l'invite de commandes classique et n'a pas besoin de PowerShell :

certutil -decode encoded.txt photo.png

Il lit un fichier, pas l'entrée standard. Il accepte le Base64 brut ainsi que les fichiers de type PEM avec marqueurs -----BEGIN ...-----, et affiche un message de succès avec le nombre d'octets écrits.

Partout : openssl

Si OpenSSL est installé, il se comporte de la même façon sur les trois systèmes :

echo 'SGVsbG8sIFdvcmxkIQ==' | openssl base64 -d -A

L'option -A lui indique que l'entrée tient sur une seule ligne. Sans elle, OpenSSL attend des retours à la ligne tous les 64 caractères et peut échouer ou ne rien renvoyer pour une longue chaîne sur une ligne.

Décoder du Base64URL (parties de JWT et jetons)

Ces outils attendent l'alphabet standard ; une entrée Base64URL contenant - et _ ou sans bourrage = provoque des erreurs. Convertissez-la d'abord. Une fonction shell réutilisable :

b64url_decode() {
  local s="${1//-/+}"
  s="${s//_//}"
  case $(( ${#s} % 4 )) in
    2) s="$s==" ;;
    3) s="$s=" ;;
  esac
  printf '%s' "$s" | base64 -d
}

# Inspect the payload of a JWT (this does not verify the signature)
b64url_decode "$(echo "$JWT" | cut -d. -f2)" | jq .

Voir Base64 vs Base64URL pour comprendre pourquoi les alphabets diffèrent, et comment inspecter les claims d'un JWT pour savoir ce que contient la charge utile. La même logique en PowerShell consiste à remplacer - et _ puis à ajouter le bourrage avant d'appeler FromBase64String.

Vérifiez ce que vous avez décodé

La sortie décodée peut être du texte ou n'importe quel fichier binaire. Avant de l'ouvrir ou de l'exécuter, examinez-la :

base64 -d encoded.txt | file -          # identify the type
base64 -d encoded.txt | xxd | head      # first bytes in hex

Les signatures aident : %PDF est un PDF, PK un ZIP ou un fichier Office, et le texte Base64 iVBORw0KGgo au début d'une chaîne est un PNG. N'exécutez jamais un fichier décodé que vous n'attendiez pas. Plus de détails dans décoder des fichiers binaires.

Dépannage

  • invalid input (Linux) ou error decoding (macOS) : la valeur contient probablement un préfixe data:...;base64,, des caractères URL-safe ou des guillemets parasites. Retirez-les d'abord.
  • La sortie est du charabia : le contenu est binaire. Écrivez-le dans un fichier plutôt que dans le terminal.
  • Rien d'affiché ou sortie tronquée : vérifiez l'absence d'un retour à la ligne, d'un -A avec OpenSSL, ou que le shell n'a pas traité +, / ou = de façon spéciale faute de guillemets.
  • Ça marche sous Linux, pas sous macOS : alternez entre -d et -D.
