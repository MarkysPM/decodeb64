JWT トークンをデコードして claims を確認する方法

2026年8月 · 6 分で読了

JWT トークンは、現代の認証システムを支える基盤です。ログインの問題をデバッグする場合でも、API がどんな claims を返しているかを確認する場合でも、あるいは OAuth 2.0 の内部の仕組みを学ぶ場合でも、JWT をデコードする方法を知っておくことは開発者にとって欠かせないスキルです。このガイドでは、その手順をステップごとに解説します。

JWT の構造

JWT(JSON Web Token)は、ドットで区切られた 3 つの部分から構成されます:

[header].[payload].[signature]

実際の JWT は次のようになります:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

各部分は標準の Base64 ではなく、Base64URL でエンコードされています。Base64URL は + を -、/ を _ に置き換え、= パディングを取り除くことで、HTTP ヘッダーや URL の中でも安全に使えるトークンになっています。

パート 1 —— ヘッダー

最初の部分は、トークンを説明する JSON オブジェクトをエンコードしています:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9

デコード結果:

{"alg":"HS256","typ":"JWT"}

「alg」フィールドは、トークンの署名にどの暗号アルゴリズムが使われたかをサーバーに伝えます。よく使われる値には HS256(HMAC と SHA-256)、RS256(RSA と SHA-256)、ES256(ECDSA と SHA-256)があります。

パート 2 —— ペイロード(claims)

2 番目の部分は claims —— トークンが持つデータ —— をエンコードしています:

eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ

デコード結果:

{"sub":"1234567890","name":"John Doe","iat":1516239022}

標準的な claim 名:

  • sub(subject)—— 通常はユーザー ID
  • iat(issued at)—— トークンが作成された Unix タイムスタンプ
  • exp(expiration)—— トークンの有効期限を表す Unix タイムスタンプ —— 「token expired」エラーをデバッグする際はここを確認
  • iss(issuer)—— トークンを発行したサーバーやサービス
  • aud(audience)—— トークンの想定される受信者
  • jti(JWT ID)—— リプレイ攻撃を防ぐために使われる、トークンの一意な識別子

カスタム claims には、ユーザーロール、権限、メールアドレス、サブスクリプションのレベルなど、アプリケーションが必要とするあらゆるデータを含めることができます。

パート 3 —— 署名(Signature)

3 番目の部分は暗号署名であり、Base64URL でエンコードされた JSON オブジェクトではありません。これは、シークレットキーを使ってヘッダーとペイロードをハッシュ化することで作成されます。読める形のテキストにデコードすることはできません。シークレットキーを持つサーバーだけがこれを検証できます。

JWT をステップごとにデコードする方法

ステップ 1: アプリケーション、ブラウザの開発者ツール、または API レスポンスから JWT 文字列をコピーします。

ステップ 2: ドットで分割します。3 つの部分に分かれますが、3 番目の部分(署名)は人間が読める形にはデコードできません。

ステップ 3: 1 番目または 2 番目の部分(ヘッダーまたはペイロード)を decodeb64.com に貼り付けます。このデコーダーは Base64URL を自動的に処理するため、- を + に、_ を / に手動で置き換える必要はありません。

ステップ 4: デコードされた JSON に claims が表示されます。認証の問題をデバッグしている場合は、まず exp フィールドを確認し、Unix タイムスタンプを読める日付に変換して、トークンが期限切れになっていないか確認しましょう。

デコードと検証の違い

重要な違いがあります。JWT をデコードすることと検証することは同じではありません。JWT のペイロードは誰でもデコードして claims を読むことができます。JWT の安全性を支えているのは署名です —— 正しいシークレットキーを持つサーバーだけが、トークンが本物であり改ざんされていないことを検証できます。

適切な JWT ライブラリを使ってサーバー側で署名を検証しないまま、アプリケーション内で JWT の claims を信用してはいけません。デコードはあくまで確認とデバッグのためのものです。

よくある JWT デバッグのシナリオ

「Token is invalid」 —— トークンの形式が不正であったり破損している可能性があります。デコーダーに貼り付けて構造を確認しましょう。

「Token is expired」 —— ペイロードをデコードし、exp claim を確認します。Unix タイムスタンプを変換して、いつトークンが期限切れになったか確認しましょう。

「Claims are wrong」 —— ペイロードをデコードして、トークンに実際にどんな claims が含まれているか確認します。多くの場合、権限変更の前にトークンが発行されていたことが原因です。

「Signature verification failed」 —— これはデコードではデバッグできません。サーバーが、ヘッダーに指定されたアルゴリズムに対して正しいシークレットキーまたは公開鍵を使用しているか確認してください。

今すぐ試す

JWT を decodeb64.com に貼り付けてみてください。このツールは Base64URL エンコーディングを自動的に検出し、ヘッダーとペイロードをデコードします。複数のトークンを一度に確認したい場合は「Decode each line separately」モードも利用できます。

JWT トークンのデコードは、認証システムを扱うバックエンド・フロントエンド開発者にとって日常的な作業です。3 つのパートから成る構造と、デコードと検証の違いを理解しておくことで、認証まわりの問題が発生したときにも落ち着いて対処できるようになります。
