Base64 と Base64URL：違いは何か？

2026年11月 · 6 分で読了

Base64 に「見える」文字列をデコーダーに貼り付けたのにエラーになった経験があれば、それはおそらく Base64URL でした。この 2 つの符号化は同じ系統で、違いはごくわずかな文字だけですが、そのわずかな文字が URL、Cookie、ファイル名、JWT の中でその文字列が無事に扱えるかどうかを左右します。

標準 Base64 を 1 分で

標準 Base64 は RFC 4648 で定義され、任意のバイト列を 64 個の印字可能文字（A–Z、a–z、0–9、そして + と /）でテキストに変換します。入力 3 バイトが出力 4 文字になります。入力の長さが 3 の倍数でない場合、出力の長さが常に 4 の倍数になるよう、末尾に = が 1 つまたは 2 つ付加されます。

たとえば、テキスト Man の 3 バイトは TWFu、Ma の 2 バイトは TWE=、1 バイトの M は TQ== になります。

Base64URL で変わること

同じ RFC には、「URL およびファイル名に安全な」Base64 と呼ばれる 2 つ目のアルファベットが定義されています。置換はちょうど 2 つで、パディングの扱いも異なります。

  • + は - になる（プラスがハイフンに）
  • / は _ になる（スラッシュがアンダースコアに）
  • パディングの = は通常省略される：規格は省略を認めており、多くの Base64URL 生成器は省略します

それ以外はすべて同じです。同じ 6 ビット単位のグループ化、同じ 33% のサイズ増加、同じデコードアルゴリズム。変わるのはアルファベットだけです。

なぜ違いがあるのか

+、/、= はいずれも、Web インフラのどこかで特別な意味を持っています。

  • / は URL やファイルシステムでパスの区切りになるため、これを含む Base64 文字列はルートやファイル名を壊すことがあります。
  • + は application/x-www-form-urlencoded のデータではスペースとして解釈されるため、クエリ文字列のパーサーが気づかないうちに値を壊すことがあります。
  • = はクエリ文字列や Cookie でキーと値を区切ります。

これらをパーセントエンコード（%2B、%2F、%3D）することもできますが、値が長くなり、うっかり二重エンコードしがちです。Base64URL は、どこでも安全な文字（英字、数字、ハイフン、アンダースコア）だけを使うことで、この問題を丸ごと避けます。

具体例

2 バイト 0xFB 0xFF を考えます。2 進数では 11111011 11111111 で、6 ビットずつに分け直すと 62、63、60 になります。これらは +、/、8 に対応します。

Standard Base64 : +/8=
Base64URL       : -_8

データは同じで、書き方が変わっただけです。2 行目に = がないことに注目してください。これが Base64URL の一般的な慣習です。

Base64URL に出会う場所

  • JWT（JSON Web Token）。 ヘッダー、ペイロード、署名はすべてパディングなしの Base64URL です。JWT トークンのデコード方法のガイドもご覧ください。
  • OAuth 2.0 と PKCE。 PKCE の code challenge は、Base64URL でエンコードされた SHA-256 ハッシュです。
  • Web Push と WebAuthn。 鍵、チャレンジ、資格情報 ID は Base64URL でやり取りされます。
  • 署名付き URL、セッション ID、短い ID。 多くのフレームワークが生成します。

標準 Base64 は、メール添付（MIME）、PEM 証明書、データ URI、そして「バイナリのかたまりをテキストフィールドに保存する」ほとんどの場面で今も標準です。

相互変換

アルゴリズムが同一なので、変換は文字の置換とパディングの追加だけです。

Base64URL から Base64 へ——文字を元に戻し、長さが 4 の倍数になるようパディングを復元します。

// JavaScript
function base64urlToBase64(s) {
  let b64 = s.replace(/-/g, '+').replace(/_/g, '/');
  while (b64.length % 4) b64 += '=';
  return b64;
}

Base64 から Base64URL へ——逆の操作で、パディングを取り除きます。

function base64ToBase64url(s) {
  return s.replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

Python では標準ライブラリにすでに補助関数があります。base64.urlsafe_b64encode() と base64.urlsafe_b64decode() です。これらは = のパディングを残すので、受け取り側がパディングなしの形式を期待する場合は自分で取り除いてください。Node.js では、Buffer.toString() と Buffer.from() に 'base64url' をエンコーディングとして渡せます。

よくある間違い

Base64URL を厳密な Base64 デコーダーでデコードする。 厳密なデコーダーは - と _ を拒否し、パディング不足を指摘します。トークンを調べるときの「invalid character」や「incorrect padding」エラーの最も多い原因です。

標準 Base64 をエンコードせずに URL に入れる。 サーバー側で + がスペースになり、デコードされたバイトが壊れます。エラーが出ないことも多いです。

パディングが常にあると思い込む。 多くのライブラリはパディングなしで出力するため、どちらの形式も受け付けるデコーダーを書きましょう。

アルファベットを混ぜる。 + と - の両方、または / と _ の両方を含む文字列は、どちらのアルファベットでも無効です。通常は 2 つのシステムが連結または編集したことを意味します。

どちらを使うべきか

値が URL、クエリ文字列、Cookie、ファイル名、HTTP ヘッダーに載る場合や、仕様（JWT、PKCE、WebAuthn）が求める場合は Base64URL を使います。MIME、PEM、データ URI、そして + や / が問題にならない保存フィールドには標準 Base64 を使います。

文字列を受け取ったもののどちらの形式か分からないときは、decodeb64.com に貼り付けてください。デコーダーが両方のアルファベットを自動検出し、パディング不足も許容するので、すぐにデコード結果が見られます。
