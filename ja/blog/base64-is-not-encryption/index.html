Base64 は暗号化ではない：セキュリティの誤解と本当のリスク

2026年11月 · 6 分で読了

「パスワードは Base64 で保存しているから安全です」。この言い回しの変種は、コードレビュー、セキュリティ監査、さらには本番インシデントの報告書にまで現れます。これは誤りであり、その誤解が危険なのは、Base64 の出力が十分に意味不明に見えて安全だと感じさせるからです。この記事では、Base64 が実際に何をしているのか、なぜ保護にならないのか、代わりに何を使うべきかを説明します。

Base64 の正体

Base64 は符号化であり、暗号ではありません。唯一の役割は、任意のバイト列を 64 個の安全な印字可能文字で表現し、メール、JSON、XML、URL、HTTP ヘッダーのようなテキスト向けのシステムをデータが通過できるようにすることです。鍵も秘密も、推測すべきアルゴリズムもありません。世界中のどの Base64 デコーダーも、同じように元へ戻します。

HTTP Basic 認証ヘッダーを例にしましょう。ユーザー名 user、パスワード password のリクエストは次を送ります。

Authorization: Basic dXNlcjpwYXNzd29yZA==

dXNlcjpwYXNzd29yZA== をどのデコーダーに貼り付けても、すぐに user:password が得られます。リクエストを読める人は誰でも認証情報を読めるため、Basic 認証は HTTPS 上でしか使ってはいけません。

符号化、暗号化、ハッシュは別物

  • 符号化（Base64、16 進数、URL エンコード）：データを媒体に収まるよう表現を変えます。誰でも元に戻せ、秘密は関与しません。目的：互換性。
  • 暗号化（AES、ChaCha20、RSA）：鍵を持つ人だけが復元できるようデータを変換します。鍵があるときだけ元に戻せます。目的：機密性。
  • ハッシュ（SHA-256、bcrypt、Argon2）：元に戻せない固定長の指紋を生成します。目的：完全性の確認とパスワードの保存。

これらは別々の問題を解決するものなので、一方を他方の代わりに使うと、黙って失敗します。「Base64 でエンコードしたパスワード」は、手順が増えただけの平文パスワードです。

混同が実害を生む場所

設定ファイル内の秘密情報。 Kubernetes の Secret オブジェクトは値を Base64 で保存します。これはバイナリの安全性のためだけです。マニフェストを読める人や kubectl get secret -o yaml を実行できる人は、すべての値をデコードできます。RBAC、保存時の暗号化、外部のシークレット管理で保護してください。

JWT のペイロード。 署名された JWT は Base64URL でエンコードされた JSON であり、暗号化されてはいません。トークンを持つ人は誰でもクレームを読めます。パスワード、個人情報、内部限定の詳細を入れてはいけません。JWT クレームのデコードと確認も参照してください。

「難読化」された API キーや URL。 API キーを Base64 文字列としてクライアントのスクリプトに隠しても、誰も止められません。数秒で見つかりデコードされ、認証情報漏えいのよくある原因です。

トークンと Cookie。 Base64 の JSON として Cookie に保存されたセッションデータは、署名や暗号化もされていない限り、ユーザーが読み、編集し、再送できます。

マルウェアとフィッシング。 攻撃者は Base64 を使って、スクリプトや URL を表面的な検査から隠します（PowerShell の -EncodedCommand が定番です）。防御側は日常的にそれをデコードします。難読化は、見る人には何も隠せません。

Base64 自体にある、より小さいが現実のリスク

  • サイズの増加。出力は入力より約 33% 大きく、大きなペイロード、モバイル回線、データベースの保存で問題になります。
  • 隠されたペイロード。Base64 は何でも無害に見えるテキストに変えるため、怪しい平文だけを探すフィルターは、その中の悪意ある内容を見逃すことがあります。セキュリティツールは、検査前にデコードすべきです。
  • 安全でないデコード済みファイル。デコードされた文字列は、実行ファイル、スクリプト、JavaScript が埋め込まれた SVG かもしれません。信頼できない出所のデコード結果は、種類を確認せずに実行したり描画したりしないでください。
  • デコードしたテキスト経由のインジェクション。ユーザー提供の Base64 をデコードし、その結果を HTML、SQL、シェルコマンドに挿入すれば、どんな生の入力とも同じインジェクションのリスクがあります。

代わりに使うもの

道具を本当の目的に合わせましょう。

  • 通信中のデータの機密性：TLS（HTTPS）。常に。
  • 保存データの機密性：AES-256-GCM や ChaCha20-Poly1305 のような認証付き暗号と、KMS やシークレット管理に置いた鍵。そのうえで、暗号文を Base64 エンコードして保存・送信できます。これこそ Base64 の正しい役割、つまりすでに保護されたバイト列の運搬です。
  • パスワードの保存：Argon2id、scrypt、bcrypt のような、遅くてソルト付きのパスワードハッシュ。可逆的に暗号化・符号化してはいけません。
  • データが改変されていないことの証明：HMAC またはデジタル署名。
  • 秘密をクライアントコードに置かない：サーバー側で保持し、短命で範囲を限定したトークンだけを公開します。

簡単なテスト

こう自問してください。「攻撃者がこの値を見たら、使えるか、読めるか？」値が Base64 でエンコードされているだけなら、答えは「はい、一瞬で」です。怪しい文字列を decodeb64.com に貼り付ければ、自分で確かめられます。デコードはブラウザー内でローカルに行われるので、トークンやヘッダーを安全に調べられます。Base64 に「隠された」秘密がアプリケーションにないかを監査する手段としても役立ちます。

Base64 は、本来の用途、つまりテキスト専用の経路でバイト列を運ぶ手段として使う限り、役に立つ正直な道具です。何も守ってはくれないので、その仕事は本物の暗号に任せましょう。
