Base64 のデコードが失敗する理由：よくある 8 つのエラーと対処法

2026年11月 · 7 分で読了

Base64 は単純な符号化ですが、デコードは思った以上によく失敗します。エラーメッセージは曖昧で（「invalid character」「incorrect padding」「malformed input」）、本当の原因は文字列そのものではなく、その文字列がどう届いたかにあることがほとんどです。ここでは、ほぼすべての失敗の裏にある 8 つの原因を、見分け方と直し方とともに紹介します。

1. パディングの欠落または誤り

症状：「Incorrect padding」（Python）、「Invalid length」（多くのライブラリ）、または黙って切り詰められる。

パディング付きの有効な Base64 文字列は、長さが 4 の倍数で、= が 0 個、1 個、または 2 個で終わります。JWT のように Base64URL を使うシステムはパディングを取り除きます。すると厳密なデコーダーは失敗します。

対処：長さが 4 の倍数になるまで = を足します。長さを 4 で割って余りが 1 になる場合、文字列は切り詰められており、パディングでは直せません。完全な値を入手してください。

2. 標準デコーダーに Base64URL を渡している

症状：- または _ を含む文字列で「Invalid character」。

URL セーフなアルファベットは + を - に、/ を _ に置き換えます。標準のアルファベットを期待するデコーダーはこれらを拒否します。詳しくは Base64 と Base64URL の記事をご覧ください。

対処：文字を元に戻す（- を +、_ を / に）か、デコーダーの URL セーフモードを使います。

3. プラス記号がスペースになった

症状：デコード結果が壊れている、または + があるはずの場所にスペースがある。

Base64 をパーセントエンコードせずにクエリ文字列やフォーム本文で送ると、サーバーは + をスペースとして解釈します。コードが見る前にデータが変わってしまいます。

対処：デコード前にスペースを + に置き換え、送信側を修正して値をパーセントエンコードするか Base64URL を使うようにします。

4. 改行と空白

症状：あるツールでは動くのに、別のツールでは失敗する。

MIME や PEM の Base64 は 1 行 64 または 76 文字で折り返されます。メール、ログ、ターミナルからコピーすると、末尾にスペースやタブが混入することもあります。空白を無視するデコーダーもあれば、無視しないものもあります。

対処：デコード前にすべての空白を取り除きます。JavaScript：s.replace(/\s+/g, '')。Python："".join(s.split())。

5. データ URI のプレフィックスが付いたまま

症状：コロンやセミコロンのある 4 または 5 文字目で「Invalid character」。

data:image/png;base64,iVBORw0... のような文字列は URI であり、純粋な Base64 ではありません。エンコードされたデータはカンマ以降だけです。構造はデータ URI ガイドをご覧ください。

対処：最初のカンマで分割し、後半をデコードします。

6. 文字列が切り詰められた、または改変された

症状：出力は正しく始まるが途中からゴミになる、またはデコーダーが不可能な長さだと報告する。

チャットアプリ、表計算、データベースの列、ログシステムは長い値を切り詰めます。表計算では文字列の一部が指数表記に変換されることもあります。PDF からコピーすると、文字が置き換わったりソフトハイフンが入ったりします。

対処：元と先の長さを比較し、列の長さ制限を確認し（VARCHAR(255) は長いトークンを切ります）、レンダリングされた文書ではなく元のソースからコピーします。

7. デコードは成功するがテキストが読めない

症状：� の文字、Ã© のような奇妙な記号、または UnicodeDecodeError が出る。

Base64 が復元するのはバイト列だけです。そのバイト列が読めるテキストかどうかは、作成時に使われた文字エンコーディングで決まります。よくある原因は次のとおりです。

  • 内容がそもそもテキストではない。画像、PDF、圧縮アーカイブ、暗号化されたデータなど。たとえば PNG は必ず ‰PNG で始まるバイト列にデコードされます。
  • テキストが UTF-16、Latin-1 などの別のエンコーディングなのに、UTF-8 としてデコードしている（またはその逆）。
  • 二重にエンコードされた、あるいは先に圧縮されている（gzip、deflate）。Base64 のあとにもう 1 段階必要。

対処：最初のバイトを見ます。PK は ZIP または Office ファイル、%PDF は PDF、1f 8b は gzip、そして Base64 自体の先頭にある iVBORw0KGgo は PNG のシグネチャです。バイナリファイルのデコードのガイドにはさらに多く載っています。

8. 二重エンコード

症状：デコードしたら、まだ Base64 に見える別の文字列が得られる。

デコード結果が eyJ（{" の Base64）や SGVs（Hel の Base64）のようなもので始まる場合、その値は 2 回エンコードされています。アプリケーションのある層がエンコードしたデータを、別の層がもう一度エンコードすると起こります。

対処：もう一度デコードし、各層がちょうど 1 回だけエンコードするようにパイプラインを修正します。

診断の手順

デコードが失敗したら、この短いリストを順に確認します。

  • 文字列の前後を取り除き、すべての空白と改行を削除する。
  • data:...;base64, プレフィックスがあれば取り除く。
  • - や _ がないか確認する。あれば Base64URL として扱う。
  • 値が URL から来たものなら、スペースを + に置き換える。
  • 長さを計算する。4 の倍数になるまでパディングし、余りが 1 なら切り詰めとみなす。
  • バイト列にデコードし、テキストとして解釈しようとする前に最初の数バイトを確認する。

手作業を省きたいなら、値を decodeb64.com に貼り付けてください。プレフィックスと空白を取り除き、標準または URL セーフなアルファベットを検出し、パディング不足を修復し、結果がテキストかバイナリファイルかを教えてくれるので、たいてい数秒で原因が分かります。
