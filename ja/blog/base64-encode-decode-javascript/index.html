JavaScript の Base64：btoa、atob と Unicode の落とし穴

2026年11月 · 7 分で読了

JavaScript には Base64 用の組み込み関数が 2 つ、btoa() と atob() あり、ASCII ならまったく問題なく動きます。問題は、テキストに絵文字、Latin-1 の範囲外のアクセント付き文字、あるいはバイナリデータが含まれた途端に始まります。このガイドでは、これらの関数が実際に何をしているのか、なぜ失敗するのか、そしてブラウザーと Node.js の両方で通用するパターンを紹介します。

基本：btoa と atob

名前は歴史的なもので、btoa は「binary to ASCII」（エンコード）、atob は「ASCII to binary」（デコード）を意味します。

btoa('Hello, World!');
// "SGVsbG8sIFdvcmxkIQ=="

atob('SGVsbG8sIFdvcmxkIQ==');
// "Hello, World!"

どちらも、すべての最新ブラウザー、Web Worker、そして現行の Node.js、Deno、Bun のグローバルとして利用できます。

Unicode の問題

重要な点は、btoa() が「テキスト」を受け取るわけではないということです。受け取るのは*バイナリ文字列*で、各文字のコードポイントが 0 から 255 の範囲にあり、1 文字が 1 バイトとして扱われます。それを超えるとエラーになります。

btoa('€');
// Uncaught InvalidCharacterError: String contains an invalid character

btoa('你好');
// Uncaught InvalidCharacterError

é（U+00E9）のような文字は 0–255 の範囲に収まるので、btoa('café') は動くように見えますが、UTF-8 ではなく Latin-1 のバイトをエンコードしています。結果を UTF-8 としてデコードする別のシステムでは、文字化けします。安全な方法は、まず文字列を UTF-8 のバイト列に変換し、そのバイト列をエンコードすることです。

Unicode テキストを正しくエンコードする

TextEncoder で UTF-8 のバイト列を取得し、バイナリ文字列に変換してから btoa() を呼びます。

function encodeBase64(text) {
  const bytes = new TextEncoder().encode(text);
  let binary = '';
  bytes.forEach(b => { binary += String.fromCharCode(b); });
  return btoa(binary);
}

encodeBase64('€');      // "4oKs"
encodeBase64('你好');   // "5L2g5aW9"

逆方向は TextDecoder を使います。

function decodeBase64(b64) {
  const binary = atob(b64);
  const bytes = Uint8Array.from(binary, c => c.charCodeAt(0));
  return new TextDecoder().decode(bytes);
}

decodeBase64('4oKs');   // "€"

非常に大きな入力では、文字列を 1 文字ずつ組み立てると遅くなります。バイトをチャンクごと（たとえば String.fromCharCode.apply で一度に 32,768 個）に処理し、速度低下とコールスタックの制限を避けましょう。

Node.js：Buffer を使う

Node.js では Buffer が UTF-8 とバイナリデータを直接扱えるため、回避策は不要です。

Buffer.from('€', 'utf8').toString('base64');
// "4oKs"

Buffer.from('4oKs', 'base64').toString('utf8');
// "€"

// Base64URL (Node.js 15.7+ and 14.18+)
Buffer.from('hello?>', 'utf8').toString('base64url');

ファイルでも Buffer が適切です。ファイルをそのまま buffer に読み込み、バイト文字列を経由せずに .toString('base64') を呼べるからです。

ブラウザーでのバイナリデータ

ユーザーが選んだファイルをエンコードするには、通常 FileReader.readAsDataURL() が最も簡単です。結果はデータ URI で、Base64 部分はカンマ以降のすべてです。

const reader = new FileReader();
reader.onload = () => {
  const dataUri = reader.result;           // "data:image/png;base64,iVBORw0..."
  const base64  = dataUri.split(',')[1];   // just the Base64 payload
};
reader.readAsDataURL(file);

逆に、Base64 をダウンロード可能なファイルや画像の URL に戻すには、Uint8Array にデコードし、Blob で包み、オブジェクト URL を作成します。

function base64ToBlob(b64, type = 'application/octet-stream') {
  const binary = atob(b64);
  const bytes = Uint8Array.from(binary, c => c.charCodeAt(0));
  return new Blob([bytes], { type });
}

const url = URL.createObjectURL(base64ToBlob(b64, 'image/png'));
img.src = url;

オンラインの Base64 画像変換ツールは、裏でこれをしています。私たちの Base64 画像変換ツールも、同じ方法でブラウザー内だけで動作するため、何もアップロードされません。

JavaScript での Base64URL

ブラウザーには、URL セーフなアルファベット向けの btoa に相当する組み込み関数がないので、文字を自分で変換します（Base64 と Base64URLを参照）。

const toBase64Url = b64 =>
  b64.replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');

const fromBase64Url = s => {
  let b64 = s.replace(/-/g, '+').replace(/_/g, '/');
  while (b64.length % 4) b64 += '=';
  return b64;
};

エラー処理

入力に Base64 のアルファベット以外の文字が含まれていると、atob() は InvalidCharacterError を投げます。ASCII の空白は無視されるので、長い文字列の途中の改行は問題ありません。現行の実装では、長さが不可能な値でない限りパディング不足も受け入れられます（長さが 4n+1 の文字列は決して有効になりません）。信頼できない入力のデコードは、必ず try/catch で囲んでください。

function safeDecode(b64) {
  try {
    return atob(b64.trim());
  } catch (e) {
    return null;   // not valid Base64
  }
}

クイックリファレンス

  • ブラウザーでの ASCII テキスト：btoa / atob。
  • 任意の Unicode テキスト：btoa や atob を TextEncoder や TextDecoder で包む。
  • Node.js：Buffer.from(...).toString('base64')。'base64url' にも対応。
  • ブラウザーでのファイル：エンコードは FileReader.readAsDataURL()、デコードは Blob と URL.createObjectURL()。
  • 文字列が有効だと決めつけない：エラーを捕捉し、空白を取り除く。

デコードがうまくいかず、問題がコードにあるのかデータにあるのか分からないときは、文字列を decodeb64.com に貼り付けてください。そこでデコードできるなら、データは正常で、バグは Unicode、パディング、URL セーフなアルファベットの扱いにあります。
