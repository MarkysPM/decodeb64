Base64 与 Base64URL：区别是什么？

2026年11月 · 6 分钟阅读

如果你曾把一个字符串粘贴到 Base64 解码器里，明明“看起来”像 Base64 却报错，那很可能它其实是 Base64URL。这两种编码同属一个家族，只在少数几个字符上不同，但正是这几个字符决定了字符串能否在 URL、Cookie、文件名或 JWT 中安全存活。

一分钟了解标准 Base64

标准 Base64 由 RFC 4648 定义，使用 64 个可打印字符把任意字节转换为文本：A–Z、a–z、0–9，再加上 + 和 /。每 3 个输入字节变成 4 个输出字符。当输入长度不是 3 的倍数时，输出末尾会补上一个或两个 =，使最终长度始终是 4 的倍数。

例如，文本 Man 的三个字节编码为 TWFu，Ma 的两个字节编码为 TWE=，单个字节 M 编码为 TQ==。

Base64URL 改变了什么

同一份 RFC 还定义了第二套字母表，常被称为“URL 与文件名安全”的 Base64。它只做两处替换，并且对填充的处理不同：

  • + 变成 -（加号换成连字符）
  • / 变成 _（斜杠换成下划线）
  • 填充符 = 通常被省略：标准允许省略，大多数 Base64URL 生成器都会这么做

其余一切都相同：同样的 6 位分组、同样 33% 的体积增长、同样的解码算法。只有字母表不同。

为什么会有这种差异

字符 +、/ 和 = 在 Web 基础设施的某些地方都有特殊含义：

  • / 在 URL 和文件系统中用来分隔路径段，因此包含它的 Base64 字符串可能破坏路由或文件名。
  • + 在 application/x-www-form-urlencoded 数据中会被解释为空格，查询字符串解析器可能悄悄把它改坏。
  • = 在查询字符串和 Cookie 中用来分隔键和值。

你可以对这些字符做百分号编码（%2B、%2F、%3D），但这会让值变长，也很容易不小心重复编码。Base64URL 只使用在任何地方都安全的字符——字母、数字、连字符和下划线——从根本上避开了这个问题。

一个具体的例子

取两个字节 0xFB 0xFF。二进制是 11111011 11111111，重新按 6 位分组得到 62、63 和 60，分别对应 +、/ 和 8：

Standard Base64 : +/8=
Base64URL       : -_8

数据完全相同，只是写法不同。注意第二行没有 =，这是 Base64URL 的通行约定。

你会在哪里遇到 Base64URL

  • JWT（JSON Web Token）。 头部、载荷和签名都是不带填充的 Base64URL。参见我们的 JWT 令牌解码指南。
  • OAuth 2.0 与 PKCE。 PKCE 的 code challenge 是经 Base64URL 编码的 SHA-256 哈希。
  • Web Push 与 WebAuthn。 密钥、挑战值和凭据 ID 都以 Base64URL 传递。
  • 签名 URL、会话标识符和短 ID，许多框架都会生成。

标准 Base64 仍然是电子邮件附件（MIME）、PEM 证书、Data URI 以及大多数“把二进制数据存进文本字段”场景的默认选择。

两者之间的转换

由于算法完全相同，转换只需替换字符并补上填充。

Base64URL 转 Base64——把字符换回去，并补齐填充，使长度成为 4 的倍数：

// JavaScript
function base64urlToBase64(s) {
  let b64 = s.replace(/-/g, '+').replace(/_/g, '/');
  while (b64.length % 4) b64 += '=';
  return b64;
}

Base64 转 Base64URL——反过来，并去掉填充：

function base64ToBase64url(s) {
  return s.replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

在 Python 中，标准库已有现成的辅助函数：base64.urlsafe_b64encode() 和 base64.urlsafe_b64decode()。注意它们会保留 = 填充，如果接收方期望无填充形式，需要自己去掉。在 Node.js 中，可以把 'base64url' 作为编码参数传给 Buffer.toString() 和 Buffer.from()。

常见错误

用严格的 Base64 解码器解码 Base64URL。 严格的解码器会拒绝 - 和 _，并抱怨缺少填充。这是检查令牌时出现“invalid character”和“incorrect padding”错误的最常见原因。

把标准 Base64 不加编码地放进 URL。 + 在服务器上会变成空格，解码出的字节被破坏，而且往往没有任何报错。

假定填充总是存在。 许多库输出的是无填充形式，所以解码器应当同时接受两种形式。

混用两种字母表。 同时包含 + 和 -，或同时包含 / 和 _ 的字符串，在两种字母表中都无效。这通常意味着两个系统拼接或修改过它。

该用哪一种？

当值需要出现在 URL、查询字符串、Cookie、文件名或 HTTP 头中，或者规范（JWT、PKCE、WebAuthn）要求时，使用 Base64URL。在 MIME、PEM、Data URI，以及 + 和 / 不会造成问题的存储字段中，使用标准 Base64。
