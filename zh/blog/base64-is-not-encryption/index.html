Base64 不是加密：安全误区与真实风险

2026年11月 · 6 分钟阅读

“密码是用 Base64 存的，所以是安全的。”这句话的各种变体出现在代码评审、安全审计，甚至生产事故报告里。它是错的，而且这种错误很危险，因为 Base64 的输出看起来足够混乱，让人觉得安全。本文说明 Base64 实际做了什么、为什么它不提供任何保护，以及应该用什么来替代。

Base64 到底是什么

Base64 是一种编码，而不是密码算法。它唯一的任务，是用 64 个安全的可打印字符表示任意字节，使数据能够通过为文本设计的系统传输：电子邮件、JSON、XML、URL、HTTP 头。它没有密钥、没有秘密、也没有需要猜测的算法。世界上每一个 Base64 解码器都用同样的方式还原它。

以 HTTP Basic 认证头为例。用户名为 user、密码为 password 的请求会发送：

Authorization: Basic dXNlcjpwYXNzd29yZA==

把 dXNlcjpwYXNzd29yZA== 粘贴进任何解码器，立刻得到 user:password。任何能读取该请求的人都能读到凭据，这就是为什么 Basic 认证只能在 HTTPS 上使用。

编码、加密与哈希是不同的东西

  • 编码（Base64、十六进制、URL 编码）：改变数据的表示形式，使其适合某种载体。任何人都能还原，不涉及秘密。目的：兼容性。
  • 加密（AES、ChaCha20、RSA）：转换数据，只有持有密钥的人才能恢复。只有用密钥才能还原。目的：机密性。
  • 哈希（SHA-256、bcrypt、Argon2）：生成无法还原的固定长度指纹。目的：完整性校验和密码存储。

由于它们解决的是不同的问题，用其中一个代替另一个会悄无声息地失败。“用 Base64 编码的密码”只是多了几个步骤的明文密码。

混淆会造成真实损害的地方

配置文件中的密钥。 Kubernetes 的 Secret 对象以 Base64 存储值，这只是为了保证二进制安全。任何能读取清单或运行 kubectl get secret -o yaml 的人都能解码所有值。请用 RBAC、静态加密和外部密钥管理器来保护它们。

JWT 载荷。 已签名的 JWT 是 Base64URL 编码的 JSON，并未加密。任何拿到令牌的人都能读取其中的声明。绝不要在里面放密码、个人数据或内部细节。参见如何解码并检查 JWT 声明。

被“混淆”的 API 密钥和 URL。 把 API 密钥作为 Base64 字符串藏在客户端脚本里，拦不住任何人。几秒钟就能找到并解码，这也是凭据泄露的常见来源。

令牌与 Cookie。 以 Base64 JSON 形式存放在 Cookie 中的会话数据，除非同时签名或加密，否则用户可以读取、修改并重新提交。

恶意软件与钓鱼。 攻击者用 Base64 让脚本和 URL 躲过粗略检查（PowerShell 的 -EncodedCommand 就是经典例子）。防御者则会例行解码它们。混淆瞒不过认真去看的人。

Base64 本身的真实（虽然较小的）风险

  • 体积增长。输出比输入大约大 33%，这对大型负载、移动网络和数据库存储都有影响。
  • 隐藏的负载。由于 Base64 能把任何东西变成看似无害的文本，只扫描可疑明文的过滤器可能漏掉其中的恶意内容。安全工具应当先解码再检查。
  • 不安全的解码文件。解码出的字符串可能是可执行文件、脚本，或内嵌 JavaScript 的 SVG。对来自不可信来源的解码内容，切勿在未检查类型的情况下运行或渲染。
  • 通过解码文本注入。如果你解码用户提供的 Base64，并把结果插入 HTML、SQL 或 shell 命令，就和任何原始输入一样存在注入风险。

应该用什么替代

让工具与真实目标相匹配：

  • 传输中保密：TLS（HTTPS）。始终如此。
  • 静态数据保密：使用 AES-256-GCM 或 ChaCha20-Poly1305 等带认证的加密，密钥存放在 KMS 或密钥管理器中。之后可以把密文编码为 Base64 来存储或发送。这才是 Base64 的正确角色：传输已经受保护的字节。
  • 存储密码：使用缓慢、加盐的密码哈希，如 Argon2id、scrypt 或 bcrypt。绝不要用可逆方式加密或编码。
  • 证明数据未被修改：HMAC 或数字签名。
  • 让密钥远离客户端代码：保存在服务器上，只暴露短期、范围受限的令牌。

一个快速测试

问自己：“如果攻击者看到这个值，能使用或读取它吗？”如果这个值只是 Base64 编码，答案是肯定的，而且是瞬间。你可以把任何可疑字符串粘贴到 decodeb64.com 来亲自验证。解码在你的浏览器本地进行，因此可以安全地检查令牌和请求头，这也是审计自己的应用中是否有“藏”在 Base64 里的密钥的好办法。

只要用在正确的地方——通过纯文本通道传输字节——Base64 就是一个有用而坦率的工具。它不保护任何东西，所以把这项工作交给真正的密码学。
