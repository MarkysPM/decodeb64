Cómo decodificar tokens JWT e inspeccionar sus claims

Agosto de 2026 · 6 min de lectura

Los tokens JWT son la columna vertebral de los sistemas de autenticación modernos. Ya sea que estés depurando un problema de inicio de sesión, inspeccionando qué claims devuelve una API, o aprendiendo cómo funciona OAuth 2.0 por dentro, saber decodificar un JWT es una habilidad esencial para cualquier desarrollador. Esta guía te lleva por el proceso paso a paso.

La estructura de un JWT

Un JWT (JSON Web Token) consta de tres partes separadas por puntos:

[header].[payload].[signature]

Un JWT real tiene este aspecto:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Cada parte usa codificación Base64URL — no Base64 estándar. Base64URL sustituye + por -, / por _, y elimina el relleno =, haciendo que el token sea seguro para usarse en cabeceras HTTP y URLs.

Parte 1 — La cabecera (Header)

La primera parte codifica un objeto JSON que describe el token:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9

Decodificado:

{"alg":"HS256","typ":"JWT"}

El campo “alg” indica al servidor qué algoritmo criptográfico se usó para firmar el token. Los valores más comunes son HS256 (HMAC con SHA-256), RS256 (RSA con SHA-256) y ES256 (ECDSA con SHA-256).

Parte 2 — El payload (Claims)

La segunda parte codifica los claims — los datos que transporta el token:

eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ

Decodificado:

{"sub":"1234567890","name":"John Doe","iat":1516239022}

Nombres de claims estándar:

  • sub (subject) — normalmente el ID del usuario
  • iat (issued at) — timestamp Unix de cuándo se creó el token
  • exp (expiration) — timestamp Unix de cuándo expira el token — revísalo al depurar errores de “token expirado”
  • iss (issuer) — el servidor o servicio que creó el token
  • aud (audience) — el destinatario previsto del token
  • jti (JWT ID) — un identificador único del token, usado para evitar ataques de repetición

Los claims personalizados pueden contener cualquier dato: roles de usuario, permisos, direcciones de correo, niveles de suscripción — lo que la aplicación necesite.

Parte 3 — La firma (Signature)

La tercera parte es una firma criptográfica, no un objeto JSON codificado en Base64URL. Se crea aplicando un hash a la cabecera y al payload con una clave secreta. No se puede decodificar a texto legible. Solo el servidor que posee la clave secreta puede verificarla.

Cómo decodificar un JWT paso a paso

Paso 1: Copia la cadena del JWT desde tu aplicación, las herramientas de desarrollador del navegador, o la respuesta de una API.

Paso 2: Divídela por los puntos. Obtendrás tres partes. La tercera parte (la firma) no se puede decodificar a texto legible.

Paso 3: Toma la primera o segunda parte (cabecera o payload) y pégala en decodeb64.com. El decodificador gestiona Base64URL automáticamente — sin necesidad de reemplazar manualmente - por + o _ por /.

Paso 4: El JSON decodificado te muestra los claims. Si estás depurando un problema de autenticación, revisa primero el campo exp — convierte el timestamp Unix a una fecha legible para ver si el token ha expirado.

Decodificar vs verificar

Una distinción crítica: decodificar un JWT no es lo mismo que verificarlo. Cualquiera puede decodificar el payload de un JWT y leer los claims. Lo que hace seguros a los JWT es la firma — solo el servidor con la clave secreta correcta puede verificar que el token es genuino y no ha sido manipulado.

Nunca confíes en los claims de un JWT dentro de tu aplicación sin verificar la firma en el servidor mediante una librería JWT adecuada. La decodificación es solo para inspección y depuración.

Escenarios comunes de depuración de JWT

“El token no es válido” — El token puede estar mal formado o corrupto. Pégalo en un decodificador para comprobar su estructura.

“El token ha expirado” — Decodifica el payload y revisa el claim exp. Convierte el timestamp Unix para confirmar cuándo expiró el token.

“Los claims son incorrectos” — Decodifica el payload para ver exactamente qué claims contiene el token. El problema suele ser que el token se emitió antes de un cambio de permisos.

“Falló la verificación de la firma” — Esto no se puede depurar decodificando. Comprueba que el servidor esté usando la clave secreta o pública correcta para el algoritmo indicado en la cabecera.
