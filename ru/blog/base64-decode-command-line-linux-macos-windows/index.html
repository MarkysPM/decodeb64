Декодирование Base64 в командной строке: Linux, macOS и Windows

Ноябрь 2026 · 6 мин чтения

Для декодирования Base64 не нужны ни браузер, ни скрипт. В каждой крупной операционной системе есть инструмент, который делает это одной строкой, — удобно, когда вы читаете логи по SSH, проверяете токен в конвейере или восстанавливаете файл из переменной CI. В этом руководстве — команды для Linux, macOS и Windows и мелкие различия, из-за которых они ломаются.

Linux: команда base64

GNU coreutils включает base64 практически в каждом дистрибутиве. Добавьте -d (или --decode) для декодирования:

echo 'SGVsbG8sIFdvcmxkIQ==' | base64 -d
# Hello, World!

Используйте printf '%s' или echo -n, когда значение берётся из переменной, чтобы завершающий перевод строки не попал во вход:

printf '%s' "$TOKEN" | base64 -d

Чтобы декодировать файл в другой файл, перенаправьте вывод. Двоичные результаты всегда отправляйте в файл, а не в терминал:

base64 -d encoded.txt > photo.png
file photo.png
# photo.png: PNG image data, 800 x 600, 8-bit/color RGBA

base64 из GNU терпит переносы строк во входных данных, но другой мусор отвергает с base64: invalid input. Опция -i (--ignore-garbage) заставляет его пропускать символы вне алфавита — это полезно, но может скрыть повреждённые данные, так что применяйте осознанно.

macOS: тот же инструмент, немного другие флаги

В macOS поставляется версия BSD. Старые релизы используют заглавную -D для декодирования, а новые принимают и -d. Если один флаг даёт ошибку, попробуйте другой:

echo 'SGVsbG8sIFdvcmxkIQ==' | base64 -D
echo 'SGVsbG8sIFdvcmxkIQ==' | base64 -d     # newer macOS versions

Инструмент BSD читает и пишет файлы с помощью -i и -o:

base64 -D -i encoded.txt -o photo.png

В macOS можно декодировать прямо из буфера обмена — это самый быстрый способ изучить только что скопированное:

pbpaste | base64 -D

В Linux аналогично используется xclip -o или wl-paste.

Windows: PowerShell

PowerShell напрямую вызывает .NET. FromBase64String возвращает байты, поэтому, если содержимое — текст, преобразуйте их в текст:

$bytes = [Convert]::FromBase64String('SGVsbG8sIFdvcmxkIQ==')
[Text.Encoding]::UTF8.GetString($bytes)
# Hello, World!

Чтобы восстановить файл из Base64:

$b64 = Get-Content .\encoded.txt -Raw
[IO.File]::WriteAllBytes("$PWD\photo.png", [Convert]::FromBase64String($b64))

.NET игнорирует пробелы и переносы строк во входных данных, поэтому файл с переносами или завершающий перевод строки от Get-Content -Raw не мешают. А вот на недопустимые символы и неверную длину он выбрасывает ошибку. Используйте [IO.File]::WriteAllBytes с полным путём, потому что .NET разрешает относительные пути относительно каталога процесса, а не вашего текущего расположения в PowerShell.

Windows: certutil

Встроенный certutil работает в классической командной строке и не требует PowerShell:

certutil -decode encoded.txt photo.png

Он читает файл, а не стандартный ввод. Принимает как «сырой» Base64, так и файлы в стиле PEM с маркерами -----BEGIN ...----- и выводит сообщение об успехе с числом записанных байтов.

Везде: openssl

Если OpenSSL установлен, он ведёт себя одинаково во всех трёх системах:

echo 'SGVsbG8sIFdvcmxkIQ==' | openssl base64 -d -A

Флаг -A сообщает, что вход находится в одной строке. Без него OpenSSL ожидает переносы строк каждые 64 символа и на длинной однострочной строке может завершиться ошибкой или ничего не вернуть.

Декодирование Base64URL (части JWT и токены)

Эти инструменты ожидают стандартный алфавит, поэтому вход Base64URL с - и _ или без дополнения = вызывает ошибки. Сначала преобразуйте его. Повторно используемая функция оболочки:

b64url_decode() {
  local s="${1//-/+}"
  s="${s//_//}"
  case $(( ${#s} % 4 )) in
    2) s="$s==" ;;
    3) s="$s=" ;;
  esac
  printf '%s' "$s" | base64 -d
}

# Inspect the payload of a JWT (this does not verify the signature)
b64url_decode "$(echo "$JWT" | cut -d. -f2)" | jq .

Почему алфавиты различаются, читайте в Base64 и Base64URL, а что содержит полезная нагрузка — в как изучить claims JWT. В PowerShell та же логика — замена - и _ плюс дополнение перед вызовом FromBase64String.

Проверьте, что вы декодировали

Декодированный вывод может быть текстом или любым двоичным файлом. Прежде чем открывать или запускать его, посмотрите на него:

base64 -d encoded.txt | file -          # identify the type
base64 -d encoded.txt | xxd | head      # first bytes in hex

Помогают сигнатуры: %PDF — это PDF, PK — ZIP или файл Office, а Base64-текст iVBORw0KGgo в начале строки — PNG. Никогда не запускайте декодированный файл, которого вы не ожидали. Подробнее — в статье о декодировании двоичных файлов.

Устранение неполадок

  • invalid input (Linux) или error decoding (macOS): значение, вероятно, содержит префикс data:...;base64,, URL-безопасные символы или лишние кавычки. Сначала уберите их.
  • Вывод — мусор: содержимое двоичное. Запишите его в файл, а не в терминал.
  • Ничего не выводится или вывод обрезан: проверьте отсутствие перевода строки, нехватку -A в OpenSSL или то, что оболочка особым образом обработала +, / или =, потому что значение не было в кавычках.
  • В Linux работает, в macOS нет: переключитесь между -d и -D.
