Base64 in der Kommandozeile dekodieren: Linux, macOS und Windows

November 2026 · 6 Min. Lesezeit

Zum Dekodieren von Base64 brauchen Sie weder Browser noch Skript. Jedes große Betriebssystem bringt ein Werkzeug mit, das es in einer Zeile erledigt, praktisch, wenn Sie Logs per SSH lesen, ein Token in einer Pipeline prüfen oder eine Datei aus einer CI-Variable wiederherstellen. Diese Anleitung behandelt die Befehle für Linux, macOS und Windows und die kleinen Unterschiede, an denen sie scheitern.

Linux: der Befehl base64

GNU coreutils enthält base64 auf praktisch jeder Distribution. Mit -d (oder --decode) wird dekodiert:

echo 'SGVsbG8sIFdvcmxkIQ==' | base64 -d
# Hello, World!

Verwenden Sie printf '%s' oder echo -n, wenn der Wert aus einer Variable stammt, damit ein abschließender Zeilenumbruch nicht Teil der Eingabe wird:

printf '%s' "$TOKEN" | base64 -d

Um eine Datei in eine andere zu dekodieren, leiten Sie die Ausgabe um. Binäre Ergebnisse immer in eine Datei schreiben, nicht ins Terminal:

base64 -d encoded.txt > photo.png
file photo.png
# photo.png: PNG image data, 800 x 600, 8-bit/color RGBA

GNU-base64 toleriert Zeilenumbrüche in der Eingabe, lehnt anderen Müll aber mit base64: invalid input ab. Die Option -i (--ignore-garbage) lässt es Zeichen außerhalb des Alphabets überspringen, was nützlich ist, aber beschädigte Daten verbergen kann; setzen Sie sie bewusst ein.

macOS: dasselbe Werkzeug, leicht andere Optionen

macOS liefert die BSD-Version. Ältere Versionen nutzen ein großes -D zum Dekodieren, neuere akzeptieren auch -d. Wenn eine Option einen Fehler liefert, probieren Sie die andere:

echo 'SGVsbG8sIFdvcmxkIQ==' | base64 -D
echo 'SGVsbG8sIFdvcmxkIQ==' | base64 -d     # newer macOS versions

Das BSD-Werkzeug liest und schreibt Dateien mit -i und -o:

base64 -D -i encoded.txt -o photo.png

Unter macOS können Sie auch direkt aus der Zwischenablage dekodieren, der schnellste Weg, etwas gerade Kopiertes zu prüfen:

pbpaste | base64 -D

Unter Linux nutzt das Äquivalent xclip -o oder wl-paste.

Windows: PowerShell

PowerShell kann .NET direkt aufrufen. FromBase64String liefert Bytes, wandeln Sie sie also in Text um, wenn der Inhalt Text ist:

$bytes = [Convert]::FromBase64String('SGVsbG8sIFdvcmxkIQ==')
[Text.Encoding]::UTF8.GetString($bytes)
# Hello, World!

Um eine Datei aus Base64 wiederherzustellen:

$b64 = Get-Content .\encoded.txt -Raw
[IO.File]::WriteAllBytes("$PWD\photo.png", [Convert]::FromBase64String($b64))

.NET ignoriert Leerraum und Zeilenumbrüche in der Eingabe, daher sind eine umbrochene Datei oder der abschließende Zeilenumbruch von Get-Content -Raw unproblematisch. Bei ungültigen Zeichen und falscher Länge wird dagegen ein Fehler ausgelöst. Verwenden Sie [IO.File]::WriteAllBytes mit vollständigem Pfad, da .NET relative Pfade gegen das Prozessverzeichnis auflöst und nicht gegen Ihren aktuellen PowerShell-Ort.

Windows: certutil

Das eingebaute certutil funktioniert in der klassischen Eingabeaufforderung und braucht kein PowerShell:

certutil -decode encoded.txt photo.png

Es liest eine Datei, nicht die Standardeingabe. Es akzeptiert rohes Base64 ebenso wie PEM-artige Dateien mit -----BEGIN ...------Markierungen und gibt eine Erfolgsmeldung mit der Zahl geschriebener Bytes aus.

Überall: openssl

Ist OpenSSL installiert, verhält es sich auf allen drei Systemen gleich:

echo 'SGVsbG8sIFdvcmxkIQ==' | openssl base64 -d -A

Das Flag -A teilt mit, dass die Eingabe in einer einzigen Zeile steht. Ohne es erwartet OpenSSL Zeilenumbrüche alle 64 Zeichen und kann bei einem langen einzeiligen String scheitern oder nichts zurückgeben.

Base64URL dekodieren (JWT-Teile und Tokens)

Diese Werkzeuge erwarten das Standardalphabet, daher erzeugt Base64URL-Eingabe mit - und _ oder ohne =-Auffüllung Fehler. Konvertieren Sie sie zuerst. Eine wiederverwendbare Shell-Funktion:

b64url_decode() {
  local s="${1//-/+}"
  s="${s//_//}"
  case $(( ${#s} % 4 )) in
    2) s="$s==" ;;
    3) s="$s=" ;;
  esac
  printf '%s' "$s" | base64 -d
}

# Inspect the payload of a JWT (this does not verify the signature)
b64url_decode "$(echo "$JWT" | cut -d. -f2)" | jq .

Siehe Base64 vs. Base64URL, warum sich die Alphabete unterscheiden, und JWT-Claims prüfen, was die Payload enthält. Dieselbe Logik in PowerShell ist ein Ersetzen von - und _ plus Auffüllen vor dem Aufruf von FromBase64String.

Prüfen, was Sie dekodiert haben

Die dekodierte Ausgabe kann Text oder eine beliebige Binärdatei sein. Bevor Sie sie öffnen oder ausführen, sehen Sie sie sich an:

base64 -d encoded.txt | file -          # identify the type
base64 -d encoded.txt | xxd | head      # first bytes in hex

Signaturen helfen: %PDF ist ein PDF, PK ist ein ZIP oder eine Office-Datei, und der Base64-Text iVBORw0KGgo am Anfang eines Strings ist ein PNG. Führen Sie niemals eine dekodierte Datei aus, die Sie nicht erwartet haben. Mehr dazu unter Binärdateien dekodieren.

Fehlerbehebung

  • invalid input (Linux) oder error decoding (macOS): Der Wert enthält wahrscheinlich ein Präfix data:...;base64,, URL-sichere Zeichen oder verirrte Anführungszeichen. Entfernen Sie diese zuerst.
  • Die Ausgabe ist Müll: Der Inhalt ist binär. In eine Datei schreiben statt ins Terminal.
  • Nichts ausgegeben oder abgeschnitten: Prüfen Sie auf einen fehlenden Zeilenumbruch, ein fehlendes -A bei OpenSSL oder darauf, dass die Shell +, / oder = besonders behandelt hat, weil der Wert nicht in Anführungszeichen stand.
  • Unter Linux geht es, unter macOS nicht: Zwischen -d und -D wechseln.

Wenn eine Kommandozeilen-Dekodierung einen Wert nicht erklärt, fügen Sie ihn in decodeb64.com ein. Es erkennt das Alphabet, repariert das Auffüllen und sagt, ob das Ergebnis Text oder eine Datei ist, alles lokal in Ihrem Browser.
