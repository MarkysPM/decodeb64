Base64 vs. Base64URL: Was ist der Unterschied?

November 2026 · 6 Min. Lesezeit

Wenn Sie schon einmal einen String in einen Base64-Decoder eingefügt und einen Fehler erhalten haben, obwohl er wie Base64 „aussah“, hatten Sie sehr wahrscheinlich Base64URL vor sich. Beide Kodierungen gehören zur selben Familie und unterscheiden sich nur in wenigen Zeichen, aber diese Zeichen entscheiden darüber, ob ein String in einer URL, einem Cookie, einem Dateinamen oder einem JWT überlebt.

Standard-Base64 in einer Minute

Standard-Base64, definiert in RFC 4648, wandelt beliebige Bytes mit 64 druckbaren Zeichen in Text um: A–Z, a–z, 0–9 sowie + und /. Je drei Eingabebytes werden zu vier Ausgabezeichen. Ist die Eingabelänge kein Vielfaches von drei, wird die Ausgabe mit einem oder zwei = aufgefüllt, sodass die Endlänge immer ein Vielfaches von vier ist.

Zum Beispiel ergeben die drei Bytes des Textes Man die Kodierung TWFu, die zwei Bytes von Ma ergeben TWE= und das einzelne Byte M ergibt TQ==.

Was Base64URL ändert

Derselbe RFC definiert ein zweites Alphabet, oft „URL- und dateinamensicher“ genannt. Es nimmt genau zwei Ersetzungen vor und behandelt das Auffüllen anders:

  • + wird zu - (Plus wird zum Bindestrich)
  • / wird zu _ (Schrägstrich wird zum Unterstrich)
  • das Auffüllen mit = entfällt meist: Der Standard erlaubt, es wegzulassen, und die meisten Base64URL-Erzeuger tun das

Alles andere ist identisch: dieselbe 6-Bit-Gruppierung, dieselben 33 % Größenzuwachs, derselbe Dekodieralgorithmus. Nur das Alphabet ändert sich.

Warum es den Unterschied gibt

Die Zeichen +, / und = haben alle irgendwo in der Web-Infrastruktur eine besondere Bedeutung:

  • / trennt Pfadsegmente in URLs und Dateisystemen, daher kann ein Base64-String damit eine Route oder einen Dateinamen zerstören.
  • + wird in application/x-www-form-urlencoded-Daten als Leerzeichen gelesen, sodass ein Query-String-Parser den Wert unbemerkt verfälschen kann.
  • = trennt Schlüssel und Werte in Query-Strings und Cookies.

Sie können diese Zeichen prozentkodieren (%2B, %2F, %3D), aber der Wert wird länger und lässt sich leicht versehentlich doppelt kodieren. Base64URL umgeht das ganze Problem, indem es nur Zeichen verwendet, die überall sicher sind: Buchstaben, Ziffern, Bindestrich und Unterstrich.

Ein konkretes Beispiel

Nehmen Sie die zwei Bytes 0xFB 0xFF. Binär sind das 11111011 11111111, was sich in die 6-Bit-Werte 62, 63 und 60 gruppiert. Diese entsprechen +, / und 8:

Standard Base64 : +/8=
Base64URL       : -_8

Die Daten sind dieselben; nur die Schreibweise hat sich geändert. Beachten Sie das fehlende = in der zweiten Zeile, die übliche Base64URL-Konvention.

Wo Ihnen Base64URL begegnet

  • JWT (JSON Web Tokens). Header, Payload und Signatur sind Base64URL ohne Auffüllung. Siehe unsere Anleitung zum Decodieren von JWT-Tokens.
  • OAuth 2.0 und PKCE. Die PKCE-Code-Challenge ist ein Base64URL-kodierter SHA-256-Hash.
  • Web Push und WebAuthn. Schlüssel, Challenges und Credential-IDs werden als Base64URL ausgetauscht.
  • Signierte URLs, Sitzungskennungen und Kurz-IDs, wie sie viele Frameworks erzeugen.

Standard-Base64 bleibt der Normalfall bei E-Mail-Anhängen (MIME), PEM-Zertifikaten, Data-URIs und den meisten Fällen von „binären Blob in ein Textfeld speichern“.

Konvertieren zwischen beiden

Da die Algorithmen identisch sind, besteht die Konvertierung nur aus Zeichenersetzung plus Auffüllen.

Base64URL zu Base64: Zeichen zurücktauschen und die Auffüllung wiederherstellen, damit die Länge ein Vielfaches von vier ist:

// JavaScript
function base64urlToBase64(s) {
  let b64 = s.replace(/-/g, '+').replace(/_/g, '/');
  while (b64.length % 4) b64 += '=';
  return b64;
}

Base64 zu Base64URL: umgekehrt, und die Auffüllung entfernen:

function base64ToBase64url(s) {
  return s.replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

In Python bietet die Standardbibliothek bereits Hilfen: base64.urlsafe_b64encode() und base64.urlsafe_b64decode(). Beachten Sie, dass sie das =-Auffüllen beibehalten; entfernen Sie es selbst, wenn das empfangende System die Form ohne Auffüllung erwartet. In Node.js können Sie 'base64url' als Kodierung an Buffer.toString() und Buffer.from() übergeben.

Häufige Fehler

Base64URL mit einem strikten Base64-Decoder dekodieren. Ein strikter Decoder lehnt - und _ ab und beanstandet fehlendes Auffüllen. Das ist die häufigste Ursache für „invalid character“ und „incorrect padding“ beim Untersuchen von Tokens.

Standard-Base64 unkodiert in eine URL setzen. Das + wird auf dem Server zum Leerzeichen und die dekodierten Bytes sind verfälscht, oft ohne jede Fehlermeldung.

Davon ausgehen, dass das Auffüllen immer vorhanden ist. Viele Bibliotheken erzeugen Ausgaben ohne Auffüllung, schreiben Sie also Decoder, die beide Formen akzeptieren.

Die Alphabete mischen. Ein String mit + und - oder mit / und _ ist in keinem der beiden Alphabete gültig. Meist wurde er von zwei Systemen zusammengefügt oder bearbeitet.

Welches sollten Sie verwenden?

Verwenden Sie Base64URL, wenn der Wert in einer URL, einem Query-String, einem Cookie, einem Dateinamen oder einem HTTP-Header transportiert wird, und immer dann, wenn eine Spezifikation (JWT, PKCE, WebAuthn) es vorschreibt. Verwenden Sie Standard-Base64 für MIME, PEM, Data-URIs und Speicherfelder, in denen + und / keine Probleme verursachen.
