JWT-Tokens decodieren und Claims prüfen

August 2026 · 6 Min. Lesezeit

JWT-Tokens sind das Rückgrat moderner Authentifizierungssysteme. Ob Sie ein Login-Problem debuggen, prüfen möchten, welche Claims eine API zurückgibt, oder verstehen wollen, wie OAuth 2.0 im Detail funktioniert — das Decodieren eines JWT zu beherrschen ist eine grundlegende Entwicklerfähigkeit. Diese Anleitung führt Sie Schritt für Schritt durch den Prozess.

Der Aufbau eines JWT

Ein JWT (JSON Web Token) besteht aus drei durch Punkte getrennten Teilen:

[header].[payload].[signature]

Ein echtes JWT sieht so aus:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Jeder Teil verwendet Base64URL-Codierung — nicht Standard-Base64. Base64URL ersetzt + durch -, / durch _ und entfernt das =-Padding, wodurch das Token sicher in HTTP-Headern und URLs verwendet werden kann.

Teil 1 — Der Header

Der erste Teil codiert ein JSON-Objekt, das das Token beschreibt:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9

Decodiert:

{"alg":"HS256","typ":"JWT"}

Das Feld „alg“ teilt dem Server mit, welcher kryptografische Algorithmus zum Signieren des Tokens verwendet wurde. Gängige Werte sind HS256 (HMAC mit SHA-256), RS256 (RSA mit SHA-256) und ES256 (ECDSA mit SHA-256).

Teil 2 — Die Payload (Claims)

Der zweite Teil codiert die Claims — die vom Token transportierten Daten:

eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ

Decodiert:

{"sub":"1234567890","name":"John Doe","iat":1516239022}

Standard-Claim-Namen:

  • sub (Subject) — in der Regel die Benutzer-ID
  • iat (Issued At) — Unix-Zeitstempel der Token-Erstellung
  • exp (Expiration) — Unix-Zeitstempel des Ablaufs — beim Debuggen von „Token abgelaufen“-Fehlern zuerst prüfen
  • iss (Issuer) — der Server bzw. Dienst, der das Token erstellt hat
  • aud (Audience) — der vorgesehene Empfänger des Tokens
  • jti (JWT ID) — eine eindeutige Kennung des Tokens, die Replay-Angriffe verhindert

Benutzerdefinierte Claims können beliebige Daten enthalten: Benutzerrollen, Berechtigungen, E-Mail-Adressen, Abo-Stufen — was auch immer die Anwendung benötigt.

Teil 3 — Die Signatur

Der dritte Teil ist eine kryptografische Signatur, kein Base64URL-codiertes JSON-Objekt. Sie entsteht durch Hashing von Header und Payload mit einem geheimen Schlüssel. Sie können sie nicht in lesbaren Text decodieren — nur der Server mit dem geheimen Schlüssel kann sie verifizieren.

So decodieren Sie ein JWT Schritt für Schritt

Schritt 1: Kopieren Sie den JWT-String aus Ihrer Anwendung, den Browser-Entwicklertools oder einer API-Antwort.

Schritt 2: Teilen Sie ihn an den Punkten. Sie erhalten drei Teile. Der dritte Teil (Signatur) lässt sich nicht in lesbaren Text decodieren.

Schritt 3: Nehmen Sie den ersten oder zweiten Teil (Header oder Payload) und fügen Sie ihn in decodeb64.com ein. Der Decoder erkennt Base64URL automatisch — Sie müssen - nicht manuell durch + oder _ durch / ersetzen.

Schritt 4: Das decodierte JSON zeigt Ihnen die Claims. Beim Debuggen eines Authentifizierungsproblems prüfen Sie zuerst das exp-Feld — wandeln Sie den Unix-Zeitstempel in ein lesbares Datum um, um zu sehen, ob das Token abgelaufen ist.

Decodieren vs. Verifizieren

Ein entscheidender Unterschied: Ein JWT zu decodieren ist nicht dasselbe wie es zu verifizieren. Jeder kann eine JWT-Payload decodieren und die Claims lesen. Was JWTs sicher macht, ist die Signatur — nur der Server mit dem richtigen geheimen Schlüssel kann bestätigen, dass das Token echt und unverändert ist.

Vertrauen Sie JWT-Claims in Ihrer Anwendung niemals, ohne die Signatur serverseitig mit einer geeigneten JWT-Bibliothek zu verifizieren. Decodieren dient nur der Inspektion und dem Debugging.

Häufige JWT-Debugging-Szenarien

„Token ist ungültig“ — Das Token könnte fehlerhaft oder beschädigt sein. Fügen Sie es in einen Decoder ein, um die Struktur zu prüfen.

„Token ist abgelaufen“ — Decodieren Sie die Payload und prüfen Sie den exp-Claim. Wandeln Sie den Unix-Zeitstempel um, um zu bestätigen, wann das Token abgelaufen ist.

„Claims sind falsch“ — Decodieren Sie die Payload, um genau zu sehen, welche Claims das Token enthält. Oft wurde das Token vor einer Berechtigungsänderung ausgestellt.

„Signaturprüfung fehlgeschlagen“ — Das lässt sich nicht durch Decodieren debuggen. Prüfen Sie, ob der Server den richtigen geheimen oder öffentlichen Schlüssel für den im Header angegebenen Algorithmus verwendet.

Jetzt ausprobieren

Fügen Sie Ihr JWT in decodeb64.com ein. Das Tool erkennt automatisch die Base64URL-Codierung und decodiert Header und Payload. Bei mehreren Tokens können Sie auch den Modus „Jede Zeile einzeln decodieren“ nutzen.

Das Decodieren von JWT-Tokens ist eine tägliche Aufgabe für Backend- und Frontend-Entwickler, die mit Authentifizierungssystemen arbeiten. Wer den dreiteiligen Aufbau und den Unterschied zwischen Decodieren und Verifizieren versteht, behält bei Authentifizierungsproblemen die Kontrolle.
