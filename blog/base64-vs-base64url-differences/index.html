Base64 vs Base64URL: What Is the Difference?

November 2026 · 6 min read

If you have ever pasted a string into a Base64 decoder and got an error even though it "looked" like Base64, there is a good chance you were holding Base64URL. The two encodings come from the same family and differ by only a few characters, but those few characters decide whether a string survives inside a URL, a cookie, a filename or a JWT.

Standard Base64 in one minute

Standard Base64, defined in RFC 4648, turns arbitrary bytes into text using 64 printable characters: A–Z, a–z, 0–9, plus + and /. Every group of three input bytes becomes four output characters. When the input length is not a multiple of three, the output is padded with one or two = signs so the final length is always a multiple of four.

For example, the three bytes of the text Man encode to TWFu, the two bytes of Ma encode to TWE=, and the single byte M encodes to TQ==.

What Base64URL changes

The same RFC defines a second alphabet, often called "URL and filename safe" Base64. It makes exactly two substitutions and treats padding differently:

  • + becomes - (plus becomes hyphen)
  • / becomes _ (slash becomes underscore)
  • = padding is usually dropped — the standard allows omitting it, and most Base64URL producers do

Everything else is identical: the same 6-bit grouping, the same 33% size overhead, the same decoding algorithm. Only the alphabet changes.

Why the difference exists

The characters +, / and = all have a special meaning somewhere in web infrastructure:

  • / separates path segments in URLs and file systems, so a Base64 string containing it can break a route or a file name.
  • + is interpreted as a space in application/x-www-form-urlencoded data, which means a query-string parser can silently corrupt it.
  • = separates keys from values in query strings and cookies.

You can percent-encode these characters (%2B, %2F, %3D), but that makes the value longer and easy to double-encode by mistake. Base64URL avoids the whole problem by using only characters that are safe everywhere: letters, digits, hyphen and underscore.

A concrete example

Take the two bytes 0xFB 0xFF. In binary that is 11111011 11111111, which regroups into the 6-bit values 62, 63 and 60. Those map to +, / and 8:

Standard Base64 : +/8=
Base64URL       : -_8

The data is the same; only the way it is written down changed. Notice the missing = in the second line, which is the usual Base64URL convention.

Where you will meet Base64URL

  • JWT (JSON Web Tokens). The header, payload and signature are all Base64URL without padding. See our guide on decoding JWT tokens.
  • OAuth 2.0 and PKCE. The PKCE code challenge is a Base64URL-encoded SHA-256 hash.
  • Web Push and WebAuthn. Keys, challenges and credential IDs are exchanged as Base64URL.
  • Signed URLs, session identifiers and short IDs generated by many frameworks.

Standard Base64 is still the default in email attachments (MIME), PEM certificates, data URIs and most "store this binary blob in a text field" situations.

Converting between the two

Because the algorithms are identical, conversion is just character replacement plus padding.

Base64URL to Base64 — swap the characters back and restore padding so the length is a multiple of four:

// JavaScript
function base64urlToBase64(s) {
  let b64 = s.replace(/-/g, '+').replace(/_/g, '/');
  while (b64.length % 4) b64 += '=';
  return b64;
}

Base64 to Base64URL — the reverse, and strip the padding:

function base64ToBase64url(s) {
  return s.replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

In Python the standard library already has helpers: base64.urlsafe_b64encode() and base64.urlsafe_b64decode(). Note that they keep the = padding, so strip it yourself if the receiving system expects the unpadded form. In Node.js you can pass 'base64url' as the encoding to Buffer.toString() and Buffer.from().

Common mistakes

Decoding Base64URL with a strict Base64 decoder. A strict decoder rejects - and _ and complains about missing padding. This is the single most common cause of "invalid character" and "incorrect padding" errors when inspecting tokens.

Putting standard Base64 in a URL without encoding it. The + turns into a space on the server and the decoded bytes come out corrupted, often with no error at all.

Assuming padding is always present. Many libraries produce unpadded output, so write decoders that tolerate both forms.

Mixing the alphabets. A string containing both + and -, or both / and _, is not valid in either alphabet. It usually means two systems concatenated or edited the value.

Which one should you use?

Use Base64URL whenever the value will travel in a URL, a query string, a cookie, a file name or an HTTP header, and whenever a specification (JWT, PKCE, WebAuthn) says so. Use standard Base64 for MIME, PEM, data URIs and storage fields where the characters + and / cause no trouble.
