How to Decode JWT Tokens and Inspect Claims

August 2026 · 6 min read

JWT tokens are the backbone of modern authentication systems. Whether you are debugging a login issue, inspecting what claims an API returns, or learning how OAuth 2.0 works under the hood, knowing how to decode a JWT is an essential developer skill. This guide walks you through the process step by step.

The Structure of a JWT

A JWT (JSON Web Token) consists of three parts separated by dots:

[header].[payload].[signature]

A real JWT looks like this:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Each part uses Base64URL encoding — not standard Base64. Base64URL replaces + with -, / with _, and removes = padding, making the token safe for use in HTTP headers and URLs.

Part 1 — The Header

The first part encodes a JSON object describing the token:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9

Decoded:

{"alg":"HS256","typ":"JWT"}

The “alg” field tells the server which cryptographic algorithm was used to sign the token. Common values include HS256 (HMAC with SHA-256), RS256 (RSA with SHA-256), and ES256 (ECDSA with SHA-256).

Part 2 — The Payload (Claims)

The second part encodes the claims — the data the token carries:

eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ

Decoded:

{"sub":"1234567890","name":"John Doe","iat":1516239022}

Standard claim names:

  • sub (subject) — typically the user ID
  • iat (issued at) — Unix timestamp when the token was created
  • exp (expiration) — Unix timestamp when the token expires — check this when debugging “token expired” errors
  • iss (issuer) — the server or service that created the token
  • aud (audience) — the intended recipient of the token
  • jti (JWT ID) — a unique identifier for the token, used to prevent replay attacks

Custom claims can contain any data: user roles, permissions, email addresses, subscription levels — whatever the application needs.

Part 3 — The Signature

The third part is a cryptographic signature, not a Base64URL-encoded JSON object. It is created by hashing the header and payload with a secret key. You cannot decode it to readable text. Only the server holding the secret key can verify it.

How to Decode a JWT Step by Step

Step 1: Copy the JWT string from your application, browser developer tools, or API response.

Step 2: Split it by the dots. You will have three parts. The third part (signature) cannot be decoded to human-readable text.

Step 3: Take the first or second part (header or payload) and paste it into decodeb64.com. The decoder handles Base64URL automatically — no need to manually replace - with + or _ with /.

Step 4: The decoded JSON shows you the claims. If you are debugging an authentication issue, check the exp field first — convert the Unix timestamp to a human-readable date to see if the token has expired.

Decoding vs Verifying

A critical distinction: decoding a JWT is not the same as verifying it. Anyone can decode a JWT payload and read the claims. What makes JWTs secure is the signature — only the server with the correct secret key can verify that the token is genuine and has not been tampered with.

Never trust JWT claims in your application without verifying the signature server-side using a proper JWT library. Decoding is for inspection and debugging only.

Common JWT Debugging Scenarios

“Token is invalid” — The token may be malformed or corrupted. Paste it into a decoder to check the structure.

“Token is expired” — Decode the payload and check the exp claim. Convert the Unix timestamp to confirm when the token expired.

“Claims are wrong” — Decode the payload to see exactly what claims the token contains. The issue is often that the token was issued before a permissions change.

“Signature verification failed” — This cannot be debugged by decoding. Check that the server is using the correct secret key or public key for the algorithm in the header.
