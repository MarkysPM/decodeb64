Why Base64 Decoding Fails: 8 Common Errors and How to Fix Them

November 2026 · 7 min read

Base64 is a simple encoding, yet decoding it fails more often than you would expect. The error messages are vague ("invalid character", "incorrect padding", "malformed input"), and the real cause is usually in how the string got to you rather than in the string itself. Here are the eight causes behind almost every failed decode, with a quick way to recognise and fix each.

1. Missing or wrong padding

Symptom: "Incorrect padding" (Python), "Invalid length" (many libraries), or silent truncation.

A valid padded Base64 string has a length that is a multiple of four, ending with zero, one or two = signs. Systems that use Base64URL, such as JWT, drop the padding. Strict decoders then fail.

Fix: add = until the length is a multiple of four. If the length divided by four leaves a remainder of 1, the string is truncated and cannot be fixed by padding; ask for the complete value.

2. Base64URL fed to a standard decoder

Symptom: "Invalid character" on a string that contains - or _.

The URL-safe alphabet replaces + with - and / with _. A decoder expecting the standard alphabet rejects those. Our article on Base64 vs Base64URL covers the full story.

Fix: swap the characters back (- to +, _ to /) or use the decoder's URL-safe mode.

3. Plus signs turned into spaces

Symptom: the decoded output is corrupted, or the string contains spaces where you expect +.

When Base64 travels in a query string or form body without percent-encoding, the server interprets + as a space. The data changes before your code ever sees it.

Fix: replace spaces with + before decoding, and fix the sender to percent-encode the value or use Base64URL.

4. Line breaks and whitespace

Symptom: works in one tool, fails in another.

MIME and PEM Base64 is wrapped at 64 or 76 characters per line. Copying from email, logs or terminals can also introduce trailing spaces and tabs. Some decoders ignore whitespace; others do not.

Fix: remove all whitespace before decoding. In JavaScript: s.replace(/\s+/g, ''). In Python: "".join(s.split()).

5. The data URI prefix is still attached

Symptom: "Invalid character" at position 4 or 5, where the colon or semicolon is.

A string like data:image/png;base64,iVBORw0... is a URI, not pure Base64. Only the part after the comma is the encoded data. See our data URI guide for the structure.

Fix: split at the first comma and decode the second half.

6. The string was truncated or altered

Symptom: the output starts correctly and then ends in garbage, or the decoder reports an impossible length.

Chat applications, spreadsheets, database columns and log systems truncate long values. Spreadsheets may also convert part of a string to scientific notation. Copy-and-paste from a PDF can replace characters or insert soft hyphens.

Fix: compare lengths between source and destination, check column limits (a VARCHAR(255) will cut a long token), and copy from the original source rather than a rendered document.

7. Decoding succeeds but the text is garbled

Symptom: you see � characters, strange symbols like Ã©, or UnicodeDecodeError.

Base64 only restores bytes. Whether those bytes are readable text depends on the character encoding used when they were created. The usual causes are:

  • The content is not text at all. It is an image, a PDF, a compressed archive or encrypted data. A PNG, for instance, always decodes to bytes that start with ‰PNG.
  • The text was UTF-16, Latin-1 or another encoding but you decode as UTF-8, or the reverse.
  • It was encoded twice or compressed first (gzip, deflate), so you need an extra step after Base64.

Fix: look at the first bytes. PK means a ZIP or Office file, %PDF is a PDF, 1f 8b is gzip, and iVBORw0KGgo in the Base64 itself is the signature of a PNG. Our guide on decoding binary files lists more.

8. Double encoding

Symptom: after decoding, you get another string that still looks like Base64.

If the decoded result starts with something like eyJ (the Base64 of {") or SGVs (the Base64 of Hel), the value was encoded twice. This happens when one layer of an application encodes data that a second layer encodes again.

Fix: decode again, then fix the pipeline so each layer encodes exactly once.

A diagnostic routine

When a decode fails, work through this short list in order:

  • Trim the string and remove all whitespace and line breaks.
  • Remove any data:...;base64, prefix.
  • Check for - or _. If present, treat it as Base64URL.
  • Replace spaces with + if the value came from a URL.
  • Compute the length. Pad to a multiple of four, and treat a remainder of 1 as truncation.
  • Decode to bytes, then inspect the first few bytes before trying to interpret them as text.

If you would rather skip the manual steps, paste the value into decodeb64.com. It strips prefixes and whitespace, detects the standard or URL-safe alphabet, repairs missing padding, and tells you whether the result is text or a binary file, which usually pinpoints the cause in seconds.
