Base64와 Base64URL: 무엇이 다를까요?

2026년 11월 · 6 분 소요

Base64처럼 "보이는" 문자열을 디코더에 붙여 넣었는데 오류가 났다면, 그것은 십중팔구 Base64URL이었을 것입니다. 두 인코딩은 같은 계열이고 몇 글자만 다르지만, 그 몇 글자가 URL, 쿠키, 파일 이름, JWT 안에서 문자열이 무사히 살아남는지를 좌우합니다.

표준 Base64를 1분 만에

RFC 4648에 정의된 표준 Base64는 64개의 출력 가능한 문자(A–Z, a–z, 0–9, 그리고 +와 /)로 임의의 바이트를 텍스트로 바꿉니다. 입력 3바이트는 출력 4문자가 됩니다. 입력 길이가 3의 배수가 아니면, 최종 길이가 항상 4의 배수가 되도록 출력 끝에 =가 한두 개 붙습니다.

예를 들어 텍스트 Man의 3바이트는 TWFu로, Ma의 2바이트는 TWE=로, 1바이트 M은 TQ==로 인코딩됩니다.

Base64URL이 바꾸는 것

같은 RFC가 흔히 "URL 및 파일 이름에 안전한" Base64라고 부르는 두 번째 알파벳을 정의합니다. 정확히 두 가지를 치환하고, 패딩을 다르게 다룹니다.

  • + 는 - 가 됩니다(더하기가 하이픈으로)
  • / 는 _ 가 됩니다(슬래시가 밑줄로)
  • = 패딩은 보통 생략됩니다: 표준이 생략을 허용하며 대부분의 Base64URL 생성기가 그렇게 합니다

나머지는 모두 같습니다. 같은 6비트 묶음, 같은 33% 크기 증가, 같은 디코딩 알고리즘. 바뀌는 것은 알파벳뿐입니다.

차이가 존재하는 이유

+, /, =는 모두 웹 인프라 어딘가에서 특별한 의미를 가집니다.

  • /는 URL과 파일 시스템에서 경로 구분자이므로, 이를 포함한 Base64 문자열은 라우트나 파일 이름을 깨뜨릴 수 있습니다.
  • +는 application/x-www-form-urlencoded 데이터에서 공백으로 해석되므로, 쿼리 문자열 파서가 값을 조용히 망가뜨릴 수 있습니다.
  • =는 쿼리 문자열과 쿠키에서 키와 값을 구분합니다.

이 문자들을 퍼센트 인코딩(%2B, %2F, %3D)할 수도 있지만, 값이 길어지고 실수로 이중 인코딩하기 쉽습니다. Base64URL은 어디서든 안전한 문자(영문자, 숫자, 하이픈, 밑줄)만 사용해 이 문제를 아예 피합니다.

구체적인 예

두 바이트 0xFB 0xFF를 봅시다. 이진수로는 11111011 11111111이며, 6비트씩 다시 묶으면 62, 63, 60이 됩니다. 이는 +, /, 8에 대응합니다.

Standard Base64 : +/8=
Base64URL       : -_8

데이터는 같고 표기법만 바뀌었습니다. 둘째 줄에 =가 없다는 점에 주목하세요. 이것이 일반적인 Base64URL 관례입니다.

Base64URL을 만나게 되는 곳

  • JWT(JSON Web Token). 헤더, 페이로드, 서명은 모두 패딩 없는 Base64URL입니다. JWT 토큰 디코딩 가이드를 참고하세요.
  • OAuth 2.0과 PKCE. PKCE의 code challenge는 Base64URL로 인코딩된 SHA-256 해시입니다.
  • Web Push와 WebAuthn. 키, 챌린지, 자격 증명 ID가 Base64URL로 교환됩니다.
  • 서명된 URL, 세션 식별자, 짧은 ID. 많은 프레임워크가 생성합니다.

표준 Base64는 이메일 첨부(MIME), PEM 인증서, 데이터 URI, 그리고 "이진 데이터를 텍스트 필드에 저장" 하는 대부분의 상황에서 여전히 기본입니다.

서로 변환하기

알고리즘이 동일하므로 변환은 문자 치환과 패딩 추가일 뿐입니다.

Base64URL에서 Base64로 — 문자를 되돌리고 길이가 4의 배수가 되도록 패딩을 복원합니다.

// JavaScript
function base64urlToBase64(s) {
  let b64 = s.replace(/-/g, '+').replace(/_/g, '/');
  while (b64.length % 4) b64 += '=';
  return b64;
}

Base64에서 Base64URL로 — 반대로, 패딩은 제거합니다.

function base64ToBase64url(s) {
  return s.replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

Python에서는 표준 라이브러리에 이미 도우미가 있습니다. base64.urlsafe_b64encode()와 base64.urlsafe_b64decode()입니다. 이 함수들은 = 패딩을 유지하므로, 받는 쪽이 패딩 없는 형식을 기대한다면 직접 제거하세요. Node.js에서는 Buffer.toString()과 Buffer.from()에 'base64url'을 인코딩으로 넘길 수 있습니다.

흔한 실수

Base64URL을 엄격한 Base64 디코더로 디코딩하기. 엄격한 디코더는 -와 _를 거부하고 패딩이 없다고 불평합니다. 토큰을 살펴볼 때 나오는 "invalid character"와 "incorrect padding" 오류의 가장 흔한 원인입니다.

표준 Base64를 인코딩 없이 URL에 넣기. 서버에서 +가 공백이 되어 디코딩된 바이트가 깨지며, 종종 아무런 오류도 나지 않습니다.

패딩이 항상 있다고 가정하기. 많은 라이브러리가 패딩 없이 출력하므로, 두 형식을 모두 허용하는 디코더를 작성하세요.

알파벳 섞기. +와 -를 모두 포함하거나 /와 _를 모두 포함하는 문자열은 어느 알파벳에서도 유효하지 않습니다. 보통 두 시스템이 이어 붙이거나 편집했다는 뜻입니다.

어느 것을 써야 할까요?

값이 URL, 쿼리 문자열, 쿠키, 파일 이름, HTTP 헤더에 실리거나 사양(JWT, PKCE, WebAuthn)이 요구할 때는 Base64URL을 사용하세요. MIME, PEM, 데이터 URI, 그리고 +와 /가 문제를 일으키지 않는 저장 필드에는 표준 Base64를 사용하세요.
