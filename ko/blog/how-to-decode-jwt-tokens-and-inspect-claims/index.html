JWT 토큰을 디코딩하고 클레임을 확인하는 방법

2026년 8월 · 6 분 소요

JWT 토큰은 현대 인증 시스템의 근간입니다. 로그인 문제를 디버깅하든, API가 반환하는 클레임을 살펴보든, OAuth 2.0의 내부 동작 원리를 배우든, JWT를 디코딩할 줄 아는 것은 개발자에게 필수적인 기술입니다. 이 가이드는 그 과정을 단계별로 안내합니다.

JWT의 구조

JWT(JSON Web Token)는 점(.)으로 구분된 세 부분으로 이루어집니다:

[header].[payload].[signature]

실제 JWT는 이런 모습입니다:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

각 부분은 표준 Base64가 아닌 Base64URL로 인코딩됩니다. Base64URL은 +를 -로, /를 _로 바꾸고 = 패딩을 제거해 HTTP 헤더와 URL에서 안전하게 사용할 수 있도록 합니다.

1부 — 헤더

첫 번째 부분은 토큰을 설명하는 JSON 객체를 인코딩합니다:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9

디코딩하면:

{"alg":"HS256","typ":"JWT"}

“alg” 필드는 토큰 서명에 사용된 암호화 알고리즘을 서버에 알려줍니다. 흔히 쓰이는 값으로는 HS256(HMAC와 SHA-256), RS256(RSA와 SHA-256), ES256(ECDSA와 SHA-256)이 있습니다.

2부 — 페이로드(클레임)

두 번째 부분은 클레임, 즉 토큰이 담고 있는 데이터를 인코딩합니다:

eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ

디코딩하면:

{"sub":"1234567890","name":"John Doe","iat":1516239022}

표준 클레임 이름:

  • sub(subject) — 보통 사용자 ID
  • iat(issued at) — 토큰이 생성된 Unix 타임스탬프
  • exp(expiration) — 토큰이 만료되는 Unix 타임스탬프 — “token expired” 오류를 디버깅할 때 확인해야 할 값
  • iss(issuer) — 토큰을 발급한 서버 또는 서비스
  • aud(audience) — 토큰이 전달되도록 의도된 수신자
  • jti(JWT ID) — 재사용(replay) 공격을 막기 위한 토큰 고유 식별자

커스텀 클레임에는 사용자 역할, 권한, 이메일 주소, 구독 등급 등 애플리케이션에 필요한 어떤 데이터든 담을 수 있습니다.

3부 — 서명

세 번째 부분은 Base64URL로 인코딩된 JSON 객체가 아니라 암호화 서명입니다. 헤더와 페이로드를 시크릿 키로 해시하여 만들어집니다. 사람이 읽을 수 있는 텍스트로 디코딩할 수 없으며, 오직 해당 시크릿 키를 가진 서버만 검증할 수 있습니다.

JWT를 단계별로 디코딩하는 방법

1단계: 애플리케이션, 브라우저 개발자 도구, 또는 API 응답에서 JWT 문자열을 복사합니다.

2단계: 점(.)을 기준으로 나눕니다. 세 부분이 나오는데, 세 번째 부분(서명)은 사람이 읽을 수 있는 텍스트로 디코딩할 수 없습니다.

3단계: 첫 번째나 두 번째 부분(헤더 또는 페이로드)을 decodeb64.com에 붙여넣습니다. 이 디코더는 Base64URL을 자동으로 처리하므로 -를 +로, _를 /로 직접 바꿀 필요가 없습니다.

4단계: 디코딩된 JSON에서 클레임을 확인할 수 있습니다. 인증 문제를 디버깅 중이라면 exp 필드부터 확인하세요 — Unix 타임스탬프를 사람이 읽을 수 있는 날짜로 변환해 토큰이 만료되었는지 확인합니다.

디코딩과 검증의 차이

중요한 차이점이 있습니다. JWT를 디코딩하는 것과 검증하는 것은 다릅니다. 누구나 JWT 페이로드를 디코딩해 클레임을 읽을 수 있습니다. JWT를 안전하게 만드는 것은 서명입니다 — 올바른 시크릿 키를 가진 서버만이 토큰이 진짜이고 변조되지 않았음을 검증할 수 있습니다.

적절한 JWT 라이브러리를 사용해 서버 측에서 서명을 검증하지 않은 JWT 클레임을 애플리케이션에서 절대 신뢰하지 마세요. 디코딩은 어디까지나 검사와 디버깅을 위한 것입니다.

흔한 JWT 디버깅 상황

“토큰이 유효하지 않습니다” — 토큰 형식이 잘못되었거나 손상되었을 수 있습니다. 디코더에 붙여넣어 구조를 확인하세요.

“토큰이 만료되었습니다” — 페이로드를 디코딩해 exp 클레임을 확인하세요. Unix 타임스탬프를 변환해 언제 만료되었는지 확인합니다.

“클레임이 잘못되었습니다” — 페이로드를 디코딩해 토큰에 실제로 어떤 클레임이 담겨 있는지 확인하세요. 대개 권한 변경 이전에 발급된 토큰이 원인입니다.

“서명 검증에 실패했습니다” — 이 문제는 디코딩만으로는 해결할 수 없습니다. 서버가 헤더의 알고리즘에 맞는 올바른 시크릿 키 또는 공개 키를 사용하고 있는지 확인하세요.
