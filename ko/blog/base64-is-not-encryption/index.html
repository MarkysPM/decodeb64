Base64는 암호화가 아닙니다: 보안 오해와 실제 위험

2026년 11월 · 6 분 소요

"비밀번호를 Base64로 저장했으니 보호되고 있습니다." 이 말의 변형은 코드 리뷰, 보안 감사, 심지어 운영 장애 보고서에도 등장합니다. 이것은 틀렸고, Base64 출력이 충분히 뒤죽박죽처럼 보여 안전하다는 느낌을 주기 때문에 이 착각은 위험합니다. 이 글은 Base64가 실제로 하는 일, 보호 기능이 전혀 없는 이유, 대신 무엇을 써야 하는지 설명합니다.

Base64의 정체

Base64는 암호가 아니라 인코딩입니다. 유일한 역할은 임의의 바이트를 안전한 64개의 출력 가능 문자로 표현해, 이메일, JSON, XML, URL, HTTP 헤더처럼 텍스트용으로 만들어진 시스템을 데이터가 통과할 수 있게 하는 것입니다. 키도, 비밀도, 추측해야 할 알고리즘도 없습니다. 세상의 모든 Base64 디코더가 똑같이 되돌립니다.

HTTP Basic 인증 헤더를 보세요. 사용자 이름 user, 비밀번호 password인 요청은 다음을 보냅니다.

Authorization: Basic dXNlcjpwYXNzd29yZA==

dXNlcjpwYXNzd29yZA==를 아무 디코더에 붙여 넣으면 즉시 user:password가 나옵니다. 요청을 읽을 수 있는 사람은 누구나 자격 증명을 읽을 수 있으므로, Basic 인증은 반드시 HTTPS 위에서만 써야 합니다.

인코딩, 암호화, 해싱은 서로 다릅니다

  • 인코딩(Base64, 16진수, URL 인코딩): 데이터가 매체에 맞도록 표현을 바꿉니다. 누구나 되돌릴 수 있고 비밀이 없습니다. 목적: 호환성.
  • 암호화(AES, ChaCha20, RSA): 키를 가진 사람만 복원할 수 있도록 데이터를 변환합니다. 키가 있어야만 되돌릴 수 있습니다. 목적: 기밀성.
  • 해싱(SHA-256, bcrypt, Argon2): 되돌릴 수 없는 고정 크기 지문을 만듭니다. 목적: 무결성 검사와 비밀번호 저장.

이 도구들은 서로 다른 문제를 풀기 때문에, 하나를 다른 것 대신 쓰면 조용히 실패합니다. "Base64로 인코딩한 비밀번호"는 단계만 늘어난 평문 비밀번호입니다.

혼동이 실제 피해를 낳는 곳

설정 파일의 비밀 정보. Kubernetes Secret 객체는 값을 Base64로 저장합니다. 이는 이진 데이터 안전성을 위한 것일 뿐입니다. 매니페스트를 읽거나 kubectl get secret -o yaml을 실행할 수 있는 사람은 모든 값을 디코딩할 수 있습니다. RBAC, 저장 시 암호화, 외부 시크릿 관리자로 보호하세요.

JWT 페이로드. 서명된 JWT는 Base64URL로 인코딩된 JSON이며 암호화되어 있지 않습니다. 토큰을 가진 사람은 누구나 클레임을 읽을 수 있습니다. 비밀번호, 개인 정보, 내부 전용 세부 정보를 넣지 마세요. JWT 클레임 디코딩과 확인을 참고하세요.

"난독화된" API 키와 URL. API 키를 Base64 문자열로 클라이언트 스크립트에 숨겨도 누구도 막지 못합니다. 몇 초면 찾아서 디코딩하며, 자격 증명 유출의 흔한 원인입니다.

토큰과 쿠키. Base64 JSON으로 쿠키에 저장된 세션 데이터는 서명이나 암호화가 함께 되어 있지 않다면 사용자가 읽고, 편집하고, 다시 제출할 수 있습니다.

악성코드와 피싱. 공격자는 Base64로 스크립트와 URL을 가벼운 검사로부터 숨깁니다(PowerShell의 -EncodedCommand가 대표적입니다). 방어하는 쪽은 이를 일상적으로 디코딩합니다. 난독화는 들여다보는 사람에게는 아무것도 숨기지 못합니다.

Base64 자체의 더 작지만 실제적인 위험

  • 크기 증가. 출력은 입력보다 약 33% 크며, 큰 페이로드, 모바일 네트워크, 데이터베이스 저장 공간에서 문제가 됩니다.
  • 숨겨진 페이로드. Base64는 무엇이든 무해해 보이는 텍스트로 바꾸기 때문에, 의심스러운 평문만 검색하는 필터는 그 안의 악성 콘텐츠를 놓칠 수 있습니다. 보안 도구는 검사 전에 디코딩해야 합니다.
  • 안전하지 않은 디코딩된 파일. 디코딩된 문자열은 실행 파일, 스크립트, 또는 JavaScript가 내장된 SVG일 수 있습니다. 신뢰할 수 없는 출처의 디코딩된 콘텐츠는 형식을 확인하지 않고 실행하거나 렌더링하지 마세요.
  • 디코딩된 텍스트를 통한 인젝션. 사용자가 제공한 Base64를 디코딩해 결과를 HTML, SQL, 셸 명령에 넣으면 다른 원시 입력과 똑같은 인젝션 위험이 있습니다.

대신 무엇을 쓸까

도구를 실제 목표에 맞추세요.

  • 전송 중 데이터의 기밀 유지: TLS(HTTPS). 항상.
  • 저장된 데이터의 기밀 유지: AES-256-GCM이나 ChaCha20-Poly1305 같은 인증된 암호화와, KMS나 시크릿 관리자에 보관된 키. 그런 다음 암호문을 Base64로 인코딩해 저장하거나 전송할 수 있습니다. 이것이 Base64의 올바른 역할, 즉 이미 보호된 바이트의 운반입니다.
  • 비밀번호 저장: Argon2id, scrypt, bcrypt 같은 느리고 솔트가 있는 비밀번호 해시. 되돌릴 수 있게 암호화하거나 인코딩하지 마세요.
  • 데이터가 변경되지 않았음을 증명: HMAC 또는 디지털 서명.
  • 비밀을 클라이언트 코드 밖에 두기: 서버에 보관하고 수명이 짧고 범위가 제한된 토큰만 노출하세요.

간단한 테스트

스스로에게 물어보세요. "공격자가 이 값을 본다면 사용하거나 읽을 수 있을까?" 값이 Base64로만 인코딩되어 있다면 답은 즉시 "예"입니다. 의심스러운 문자열을 decodeb64.com에 붙여 넣어 직접 확인할 수 있습니다. 디코딩은 브라우저 안에서 로컬로 이루어지므로 토큰과 헤더를 안전하게 살펴볼 수 있고, Base64에 "숨겨진" 비밀이 애플리케이션에 있는지 점검하는 데도 유용합니다.

Base64는 본래 용도, 즉 텍스트 전용 채널로 바이트를 운반하는 수단으로 쓰는 한 유용하고 정직한 도구입니다. 아무것도 보호하지 않으니, 그 일은 진짜 암호학에 맡기세요.
