Base64 não é criptografia: mitos de segurança e riscos reais

Novembro de 2026 · 6 min de leitura

"A senha está guardada em Base64, então está protegida." Versões dessa frase aparecem em revisões de código, auditorias de segurança e até em relatórios de incidentes em produção. Está errada, e o erro é perigoso porque a saída do Base64 parece embaralhada o bastante para passar sensação de segurança. Este artigo explica o que o Base64 realmente faz, por que não oferece proteção e o que usar no lugar.

O que o Base64 realmente é

O Base64 é uma codificação, não uma cifra. Seu único trabalho é representar bytes arbitrários com 64 caracteres imprimíveis seguros para que os dados possam trafegar por sistemas feitos para texto: e-mail, JSON, XML, URLs, cabeçalhos HTTP. Não há chave, segredo nem algoritmo a adivinhar. Todo decodificador Base64 do mundo o reverte do mesmo jeito.

Veja o cabeçalho de autenticação HTTP Basic. Uma requisição com usuário user e senha password envia:

Authorization: Basic dXNlcjpwYXNzd29yZA==

Cole dXNlcjpwYXNzd29yZA== em qualquer decodificador e você obtém user:password na hora. Quem consegue ler a requisição lê as credenciais, e por isso o Basic auth só deve ser usado sobre HTTPS.

Codificação, criptografia e hash são coisas diferentes

  • Codificação (Base64, hex, codificação de URL): muda a representação dos dados para caberem em um meio. Reversível por qualquer pessoa, sem segredo. Finalidade: compatibilidade.
  • Criptografia (AES, ChaCha20, RSA): transforma os dados para que só quem tem a chave consiga recuperá-los. Reversível apenas com a chave. Finalidade: confidencialidade.
  • Hash (SHA-256, bcrypt, Argon2): produz uma impressão digital de tamanho fixo que não pode ser revertida. Finalidade: verificação de integridade e armazenamento de senhas.

Como resolvem problemas diferentes, usar um no lugar de outro falha em silêncio. Uma "senha codificada em Base64" é uma senha em texto puro com passos extras.

Onde a confusão causa dano real

Segredos em arquivos de configuração. Os objetos Secret do Kubernetes guardam valores em Base64. Isso é só por segurança binária. Quem consegue ler o manifesto ou executar kubectl get secret -o yaml decodifica todos os valores. Proteja-os com RBAC, criptografia em repouso e um gerenciador de segredos externo.

Payloads de JWT. Um JWT assinado é JSON codificado em Base64URL, não criptografado. Quem tiver o token lê os claims. Nunca coloque senhas, dados pessoais ou detalhes internos neles. Veja como decodificar e inspecionar claims de JWT.

Chaves de API e URLs "ofuscadas". Esconder uma chave de API em um script do cliente como string Base64 não detém ninguém. Encontra-se e decodifica-se em segundos, e é uma fonte comum de credenciais vazadas.

Tokens e cookies. Dados de sessão guardados em um cookie como JSON em Base64 podem ser lidos, editados e reenviados pelo usuário, a menos que também sejam assinados ou criptografados.

Malware e phishing. Atacantes usam Base64 para esconder scripts e URLs de uma inspeção casual (o -EncodedCommand do PowerShell é um clássico). Defensores os decodificam rotineiramente. A ofuscação não esconde nada de quem olha.

Riscos reais, ainda que menores, do próprio Base64

  • Aumento de tamanho. A saída é cerca de 33 % maior que a entrada, o que importa em cargas grandes, redes móveis e armazenamento em banco de dados.
  • Cargas ocultas. Como o Base64 transforma qualquer coisa em texto de aparência inofensiva, filtros que só procuram texto suspeito podem deixar passar conteúdo malicioso dentro dele. Ferramentas de segurança devem decodificar antes de inspecionar.
  • Arquivos decodificados inseguros. Uma string decodificada pode ser um executável, um script ou um SVG com JavaScript embutido. Nunca execute nem renderize conteúdo decodificado de fonte não confiável sem checar o tipo.
  • Injeção via texto decodificado. Se você decodifica Base64 fornecido pelo usuário e insere o resultado em HTML, SQL ou um comando de shell, tem o mesmo risco de injeção de qualquer entrada bruta.

O que usar no lugar

Combine a ferramenta com o objetivo real:

  • Manter dados confidenciais em trânsito: TLS (HTTPS). Sempre.
  • Manter dados confidenciais em repouso: criptografia autenticada como AES-256-GCM ou ChaCha20-Poly1305 com chaves guardadas em um KMS ou gerenciador de segredos. Depois você pode codificar o texto cifrado em Base64 para armazenar ou enviar. Esse é o papel correto do Base64: transportar bytes já protegidos.
  • Armazenar senhas: um hash de senha lento e com salt, como Argon2id, scrypt ou bcrypt. Nunca as criptografe ou codifique de forma reversível.
  • Provar que os dados não foram alterados: um HMAC ou uma assinatura digital.
  • Manter segredos fora do código do cliente: guarde-os no servidor e exponha apenas tokens de curta duração e escopo limitado.

Um teste rápido

Pergunte: "Se um atacante visse este valor, conseguiria usá-lo ou lê-lo?". Se o valor está apenas codificado em Base64, a resposta é sim, instantaneamente. Você pode comprovar colando qualquer string suspeita em decodeb64.com. A decodificação acontece localmente no seu navegador, então você pode inspecionar tokens e cabeçalhos com segurança, o que também é uma boa forma de auditar sua aplicação em busca de segredos "escondidos" em Base64.

O Base64 é uma ferramenta útil e honesta, desde que usada pelo que é: uma forma de transportar bytes por canais só de texto. Ele não protege nada, então deixe a criptografia de verdade fazer esse trabalho.
