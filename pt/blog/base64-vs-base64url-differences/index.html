Base64 vs Base64URL: qual é a diferença?

Novembro de 2026 · 6 min de leitura

Se você já colou uma string em um decodificador Base64 e recebeu um erro mesmo ela "parecendo" Base64, provavelmente estava com Base64URL. As duas codificações são da mesma família e diferem em pouquíssimos caracteres, mas esses poucos caracteres decidem se uma string sobrevive dentro de uma URL, um cookie, um nome de arquivo ou um JWT.

Base64 padrão em um minuto

O Base64 padrão, definido na RFC 4648, transforma bytes arbitrários em texto usando 64 caracteres imprimíveis: A–Z, a–z, 0–9, mais + e /. Cada grupo de três bytes vira quatro caracteres. Quando o tamanho da entrada não é múltiplo de três, a saída recebe um ou dois sinais = de preenchimento para que o tamanho final seja sempre múltiplo de quatro.

Por exemplo, os três bytes do texto Man viram TWFu, os dois bytes de Ma viram TWE= e o byte único M vira TQ==.

O que o Base64URL muda

A mesma RFC define um segundo alfabeto, chamado "seguro para URL e nomes de arquivo". Ele faz exatamente duas substituições e trata o preenchimento de outro modo:

  • + vira - (o sinal de mais vira hífen)
  • / vira _ (a barra vira sublinhado)
  • o preenchimento = geralmente é removido: o padrão permite omiti-lo e a maioria dos geradores de Base64URL o faz

Todo o resto é idêntico: o mesmo agrupamento de 6 bits, o mesmo aumento de 33 % no tamanho e o mesmo algoritmo de decodificação. Só o alfabeto muda.

Por que a diferença existe

Os caracteres +, / e = têm significado especial em algum ponto da infraestrutura web:

  • / separa segmentos de caminho em URLs e sistemas de arquivos, então uma string Base64 que o contenha pode quebrar uma rota ou um nome de arquivo.
  • + é interpretado como espaço em dados application/x-www-form-urlencoded, o que significa que um parser de query string pode corrompê-lo silenciosamente.
  • = separa chaves e valores em query strings e cookies.

Dá para codificar esses caracteres com porcentagem (%2B, %2F, %3D), mas o valor fica maior e é fácil codificar duas vezes sem querer. O Base64URL evita todo o problema usando apenas caracteres seguros em qualquer lugar: letras, dígitos, hífen e sublinhado.

Um exemplo concreto

Pegue os dois bytes 0xFB 0xFF. Em binário são 11111011 11111111, que se reagrupam nos valores de 6 bits 62, 63 e 60. Eles correspondem a +, / e 8:

Standard Base64 : +/8=
Base64URL       : -_8

Os dados são os mesmos; só mudou a forma de escrevê-los. Repare que falta o = na segunda linha, a convenção habitual do Base64URL.

Onde você vai encontrar Base64URL

  • JWT (JSON Web Tokens). O cabeçalho, o payload e a assinatura são Base64URL sem preenchimento. Veja nosso guia sobre como decodificar tokens JWT.
  • OAuth 2.0 e PKCE. O code challenge do PKCE é um hash SHA-256 codificado em Base64URL.
  • Web Push e WebAuthn. Chaves, desafios e IDs de credenciais são trocados em Base64URL.
  • URLs assinadas, identificadores de sessão e IDs curtos gerados por muitos frameworks.

O Base64 padrão continua sendo o padrão em anexos de e-mail (MIME), certificados PEM, data URIs e na maioria dos casos de "guardar um blob binário em um campo de texto".

Convertendo entre os dois

Como os algoritmos são idênticos, a conversão é só trocar caracteres e adicionar preenchimento.

Base64URL para Base64: troque os caracteres de volta e restaure o preenchimento para que o tamanho seja múltiplo de quatro:

// JavaScript
function base64urlToBase64(s) {
  let b64 = s.replace(/-/g, '+').replace(/_/g, '/');
  while (b64.length % 4) b64 += '=';
  return b64;
}

Base64 para Base64URL: o inverso, removendo o preenchimento:

function base64ToBase64url(s) {
  return s.replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
}

Em Python a biblioteca padrão já tem auxiliares: base64.urlsafe_b64encode() e base64.urlsafe_b64decode(). Eles mantêm o preenchimento =, então remova você mesmo se o sistema receptor esperar a forma sem preenchimento. No Node.js você pode passar 'base64url' como codificação para Buffer.toString() e Buffer.from().

Erros comuns

Decodificar Base64URL com um decodificador Base64 estrito. Um decodificador estrito rejeita - e _ e reclama da falta de preenchimento. É a causa mais comum dos erros "invalid character" e "incorrect padding" ao inspecionar tokens.

Colocar Base64 padrão em uma URL sem codificar. O + vira espaço no servidor e os bytes decodificados saem corrompidos, muitas vezes sem nenhum erro.

Presumir que o preenchimento sempre existe. Muitas bibliotecas geram saída sem preenchimento, então escreva decodificadores que aceitem as duas formas.

Misturar os alfabetos. Uma string com + e -, ou / e _, não é válida em nenhum dos dois. Em geral significa que dois sistemas a concatenaram ou editaram.

Qual usar?

Use Base64URL quando o valor trafegar em uma URL, query string, cookie, nome de arquivo ou cabeçalho HTTP, e sempre que uma especificação (JWT, PKCE, WebAuthn) pedir. Use Base64 padrão para MIME, PEM, data URIs e campos de armazenamento onde + e / não causam problema.

Quando receber uma string e não souber qual é a variante, cole-a em decodeb64.com. O decodificador detecta os dois alfabetos automaticamente e tolera a falta de preenchimento, então você vê o conteúdo decodificado na hora.
